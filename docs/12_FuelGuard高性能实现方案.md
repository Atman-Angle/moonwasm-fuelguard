# FuelGuard 高性能实现方案

本文负责FuelGuard自己的分析算法、数据结构、代码生成和优化路径；总体边界服从 [06](06_架构设计_MoonWasm_Instrument.md)，验收服从 [09](09_验证与验收计划.md)。[10](10_成熟项目参考与性能决策.md) 仅记录参考依据，不定义实现规范。

## 1. 实现归属和交付边界

FuelGuard以MoonBit自行实现：支持策略、计费块划分、费用模型、动态费用改写、栈成本分析与包装、增长限制、索引/引用计划、诊断映射、候选布局选择和结果报告。

starshine仅承担已有的解析、类型验证和编码基础设施，不替代上述算法。wasmoon负责执行，Wasmtime/wasm-tools负责独立测试；wasm-instrument/Binaryen不进入生产依赖，不生成产品的插桩代码，也不作为运行期回退路径。纯MoonBit插桩核心不需要Rust/C++工具即可生成产物。

自身正确性与性能必须由自身实现的测试和基准证明。外部对照可提供研究数据，但不代替本项目验收。

## 2. 默认实现路线

第一个可验收实现固定为P0：结构化计费块分析 + 正常路径内联扣费 + 内联失败诊断 + 动态操作保存一次参数 + 按资源类型复用Growth helper + 调用前Stack预留。

P0提供清晰的语义和性能基线；此处“默认”不是已证明最快。后续P1/P2保持相同费用模型、计费点、输入和诊断契约，由实测决定生产布局。不能把核心方案写成“以后挑一个上游实现”。

## 3. 数据结构与构建期成本

以下是私有结构的语义设计，不承诺公开API或当前已存在同名文件。

| 结构 | 内容 | 性能目的 |
| --- | --- | --- |
| ModuleIndex | type/function/global/import的密集索引数组、函数签名、资源描述 | 建表一次，函数处理中不反复扫描全module |
| FunctionFacts | 参数/local、原始节点编号、控制栈、指令效果、静态栈峰值 | 一次记录多个分析所需事实，避免重复解码 |
| MeterSite | 原始函数/指令序号、块区间、静态费用、动态规则ID、正常/失败模板ID | 在代码生成之前固定计费语义 |
| FunctionPlan | 追加local、改写点、输出容量估计、helper调用和包装目标 | 单函数按序重建，避免反复拼接数组 |
| SemanticPlan | 跨布局共用的原始映射、canonical site、费用与统一栈模型 | 固定预算语义，避免各候选重复定义计费 |
| InstrumentPlan | 每候选函数计划、追加项目、模板和引用改写清单 | 生成前冻结数量、签名、索引和包装结构 |
| StackLayout | 统一 C(f)、该布局 A(layout,f)、模板/入口余量及核验结果 | 构建期核验 A <= C，运行期使用共享常量 |

使用数组按函数/类型索引访问；helper签名按参数、返回值和用途去重，哈希表只用于查找，不使用其遍历顺序分配输出索引。追加顺序按固定函数序和模板枚举序，site ID按原始指令遍历序分配。

阶段对象依次冻结：SemanticPlan → 候选 InstrumentPlan → 最终 StackLayout。结构计划可引用尚待计算的成本符号；最终分析只填入定型的成本常量并生成新的不可变结果，不再新增项目或改签名。常量编码造成字节长度变化不等于索引结构变化。若模板结构需要变化，重新规划该候选；禁止分析和生成相互递归直到碰巧收敛。

解码和编码各一次；原始分析、各次改写和最终栈分析均为有限次数遍历。实现目标为O(N+R+G)的分析/生成时间和内存，N为输入指令/元数据规模，R为待改写引用数，G为生成指令数；独立验证器的复杂度另计，不声称整个依赖栈都严格线性。逐pass校验继续保留。

显式工作栈代替对任意深度输入的宿主递归；解码器若不能施加深度/数量限制，必须先增加有界预检或修复依赖能力，不能在无界解码完成后才声称防住恶意嵌套。

## 4. 计费块算法

1. 预遍历原始函数，为指令分配稳定编号，维护结构化控制帧与分支目标。
2. 在函数入口、分支目标、循环回边入口、条件路径、调用以及动态/可能trap/外部副作用边界建立计费点；仅合并必然顺序执行且符合预扣契约的片段。
3. 对每片段累加冻结权重，检查构建期溢出。call静态费用在调用前，callee自己的计费在callee内，不重复包含callee指令。
4. 建立显式控制边，审计所有可循环路径均经过正成本点；费用表禁止形成零费用执行环。递归同样必须包含正费用调用/函数路径。
5. 对每个动态操作记录参数类型和原始操作数顺序。代码生成阶段按原顺序保存操作数一次，完成资源检查和动态收费后恢复操作数执行原指令。

保守边界不要求单指令块。例如无 trap、无可观察副作用的必经前缀可以和末尾边界指令合并收费；不默认给每条 load/store 独立插检查。具体分割规则及预扣效果以冻结的模型边界表为准，所有候选复用同一 SemanticPlan。SIMD 指令自 S25 起全部拒绝（申报书范围），费用表不含 SIMD 条目；独立预言机与差分语料不含 SIMD 路径。

块划分属于费用模型语义，在同一模型版本内固定。布局优化不能把未执行分支收费、跨调用缓存余额或移动失败位置。[fuel-v1.2 边界表](implementation/fuel-v1.2.md)记录 S26 候选的 join-span 划分、预扣及冷路径指令级诊断。

## 5. Fuel热路径与动态费用

P0静态扣费语义伪代码如下，实际MoonBit负责生成Wasm指令：

```text
remaining = fuel_global
if remaining < block_cost:
    trap_code = 1
    trap_site = site_id
    unreachable
fuel_global = remaining - block_cost
execute original block
```

remaining使用每函数追加的可复用i64临时local；同函数静态站点共用，跨函数不能共享。正常路径一次global读、一次写，无新增函数调用、无site写。失败直接内联写code/site并trap，P0不额外调用失败helper，避免栈余量不足时诊断本身先失败。

动态费用cost=a+b*n的a/b为版本化非负常量，n由原始unsigned参数拓宽。b=0单独处理；b>0时先判断n是否超过可表示上界，再计算并检查剩余额度。允许将静态系数检查常量折叠，但不能把运行期越界算术当作正常费用。静态基础费用与动态附加费用必须在模型中分开列出，防止重复收费。动态数学成本超过 i64 最大值时在该 site 报 code 1，不执行溢出乘加。

生产代码不把fuel长期缓存在函数local或全局优化缓存中：调用、递归和import边界使该优化需要额外证明。首版仅在单个扣费模板内部复用读取值。

## 6. Growth与Stack的性能实现

Growth按memory/table元素类型复用本地helper，统一执行unsigned容量检查、动态收费与原始grow；helper本身不重复收Fuel。bulk copy/fill等非grow操作采用其独立模板，不能复用不匹配的引用/操作数签名。

Stack对原始直接调用使用统一常量 C(callee)，不在运行期查表。检查采用available与cost比较后减法，返回时在已知不变式下归还；深度同样先比较再更新，不发生计数回绕。export/start/间接调用使用计划内包装，覆盖与拒绝范围按06执行。

分析顺序：先冻结共享语义和候选结构（含 Stack 模板/包装布局），生成 Fuel/Growth 并验证，最后结合固定 Stack 模板计算 A(layout,f) 并核验 A <= C。C(f) 来自独立版本化的共同模板上界，覆盖所有声明候选；无需在产品中生成和运行三套计费器来求 C。候选超出 C 时构建失败，改变 C 须升级栈模型并重新验收。填入常量并完成 Stack 改写后再校验，分析不反向改变冻结结构。

生成 helper 构成有界、无递归辅助图。C(f) 只描述单个原始逻辑帧及其辅助开销，不递归展开原始调用图；原始递归由运行期逐帧预留累计。v128 local 与 v128 操作数栈值按 16 字节保守计入，不得按 i32 等价估算（S01 实测真实负载最多 48 个 v128 local、含 v128 的签名与 multi-value 结果）。顺序/互斥辅助路径取 max，嵌套 helper 链相加，挂起 caller 的预留在 callee 执行期间继续保留；跨原函数调用仍存活的 wrapper 必须明确归属且不重算。间接 wrapper 的入口临时开销在调用者预算中覆盖，外部入口 wrapper 使用认证入口余量。参数、返回值及冷诊断路径均纳入上界。

这些核验在构建期完成。原始调用处仍只做一组常量栈/深度预留并在返回时释放；已被覆盖的 helper/wrapper 不新增用户预算事件或逻辑深度。导入调用边界按原始调用计层，宿主内部仍遵守部署契约。统一预留可能更保守，但不自动增加动态检查次数。先栈后深度、间接目标检查、外部入口及动态溢出的错误顺序按需求 05 执行。

P0不删除叶函数Stack检查。若以后优化静态可证安全的叶路径，必须同时证明临时栈、深度语义和所有预算下错误优先级保持，否则作为新profile重新验收。

## 7. 本项目候选布局和选择

| 候选 | 本项目实现内容 | 假设与主要风险 |
| --- | --- | --- |
| P0 | 静态扣费及失败诊断内联；共享Growth helper | 减少热路径调用，可能增加体积 |
| P1 | 共享本地charge函数接收cost/site；共享Growth helper | 减小重复代码，可能增加调用和栈成本 |
| P2 | 使用被冻结的静态选择规则，在P0/P1模板间选择 | 折衷速度/体积，规则若过度拟合会损害未见负载 |

三个候选均由FuelGuard自己的生成器实现，共享计费 site、费用、统一 C(f) 和逻辑调用事件。StackLayout 按各自生成代码重新计算 A 并核验共同上界，不重新定义各候选的用户栈收费；包含临界栈/Fuel/深度组合的诊断和输出前缀必须一致。无需外部优化器参与即可生成和测试。

P2规则只能使用原模块的静态特征，例如块数、模板重复数、循环位置；不能根据当前机器或隐藏训练数据在运行时改写规则。规则和阈值作为codegen版本写入manifest；同输入/配置/版本必须输出同一产物。

在调优集上选择 P2 阈值并比较 P0/P1/P2，按 09 的预算和双引擎规则选定默认布局，冻结规则、模型、候选源码和哈希。接近噪声范围时优先更小、更简单的方案，不预定 P2 获胜。最终独立验收集仅确认已冻结默认是否达标；其他候选可同时报告，不据该集合切换默认。任何基于验收结果的调参或换默认都使该集合转为调优资料，保留失败数据并另建独立确认集。

## 8. 测量、责任与退出条件

核心指标均来自FuelGuard自身：计费点数、生成指令/函数/local数、动态检查数、各阶段耗时、峰值内存、产物字节数，以及完整保护在两引擎的执行中位数/p95。这些静态计数只用于解释性能，不替代实测。

U3完成独立计费预言机；U4交付本项目plan/P0；U5/U6交付Growth/Stack；U9实现P1/P2并提供消融比较。每个候选附对应源码commit、配置、产物哈希和09的验收证据。

达不到门槛时，依据热点修改本项目实现，并重做语义与性能验证；不能改用外部gas工具生成产物后仍将成绩归为FuelGuard。依赖库自身耗时可以单列，但仍计入用户端到端结果，不从总成本中隐藏。

本方案的完成条件是FuelGuard自身产物通过A01-A24，不是完成参考调研，也不是跑通外部项目。现阶段所有性能收益均为待验证假设。
