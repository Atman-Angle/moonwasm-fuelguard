## 2. 检查方式（规范正文）

### 2.1 Fuel（fuel-v2 计费模型）

出处：申报书"Fuel/Budget Pass"段全部原文承诺。

1. **版本化权重表**。指令权重随 `fuel-v2` 版本发布；表内不得出现零费用可循环路径——依据为申报书验收产物"无限循环在有限 Fuel 下终止"。
2. **计费块（span）划分**：仅在函数入口、分支臂/汇合点、循环回边、return/unreachable 出口切分；**直线合并不设上限**（ADR-0001）。空臂无需站点；唯一落穿的显式 else 与后续指令共用 span；分支指令计入当前 span 并结束它。
3. **入口预扣**：span 入口一次性预扣静态总费用 W；call 的静态费用记在调用点所在 span，callee 自身计费在 callee 内，不重复。
4. **热路径**：内联 debit-first（读余额 → 减 W → 写回 → 判符号 → 失败分支），每 span 一次；多 span 函数用 i64 local 缓存余额，在调用前发布、返回后重载、可陷阱操作前与函数出口同步。不新增扣费用局部变量的跨函数共享。
5. **冷路径**：模块级共享失败 helper，统一写诊断并 trap；不再维护 span 内逐指令回放。
6. **失败 site**：触发预扣的 span 首条源指令（ADR-0001）。满足申报书"诊断包含失败类型和原始指令位置"。
7. **i64 预算与溢出**：预算范围 `[1, 2^63−1]`，成功扣费后余额仍在 `[0, 2^63−1]`；B−W 符号判据仅用于静态费用，禁止回绕（申报书"使用检查溢出的 i64 预算"）。
8. **动态费用**：`cost = a + b·n`，a/b 为版本化非负常量，n 由原始 unsigned 参数拓宽；操作数按原顺序保存一次、检查收费后恢复执行原指令；b>0 时先判 n 上界再乘加，超 i64 同 site 报 code 1（申报书"对内存复制、填充和增长按请求长度追加动态费用"）。

### 2.2 Stack Height Limiter

出处：申报书"Stack Height Limiter"段全部原文承诺。

1. 原始调用前预留统一版本化常量 C，正常返回释放；覆盖直接调用、间接调用、导出与 Wasm start 入口（计划内包装）。
2. 成本覆盖参数、局部变量、操作数栈峰值、帧常量及生成 helper/wrapper；统一 C 与各函数实际布局 A 的核验 **A ≤ C 在构建期完成**；已覆盖的 helper/wrapper 不再新增现场检查。
3. 生成 helper 构成有界无环辅助图；wrapper 对原函数的调用按预算边界分账，不重复预留。
4. 打包表示为**唯一**栈路径：两上限与全部 C 须容纳于 31 位正数，否则配置在解析时明确拒绝；不保留双 i64 计数器回退路径（ADR-0003）。
5. 支配检查复用：同一调用帧内记住已通过检查的最大被调帧费用，下一直接调用费用不高于该值时免重复检查；预留语义隐含于该检查。导入、间接调用及入口包装保留显式预留与归还。
6. v128 local 与操作数栈值按 16 字节保守计入（维持现行 stack-v1 规则）。
7. trap 后废弃实例；宿主重入拒绝。

### 2.3 Growth 与导入控制

出处：申报书"Growth 与导入控制"段。维持现行实现形态（按资源类型复用本地 helper、unsigned 差值、动态费用模板），不在本次重设计范围：

- memory/table 初始容量超限拒绝；运行期超限按 code 2/3 trap；
- 上限内的原始 grow 保留底层失败返回值，已收动态费用不退款；
- 导入允许列表 module/name 二元组精确匹配，默认拒绝未声明导入。

### 2.4 诊断 ABI

出处：申报书"运行适配与诊断"段。

- `__moonwasm_trap_code` 0..5（1 Fuel、2/3 Memory/Table、4 Stack、5 Depth）+ 稳定 site 导出；
- 受控失败与程序自身 trap 可区分；成功路径不写 site；
- start/实例化失败拿不到实例时报告 diagnostic-unavailable，不推断 code。

### 2.5 交付形态

出处：申报书"CLI/工程"与"Pass 管线 + 库 API"段。

1. **单一默认布局**（compact v2 血统：合并 span + 内联 debit-first + 函数内缓存 + 打包栈 + 支配检查复用），ADR-0002。其余六个布局（P0/P1/P2/p2-prefix/join-span/join-span-cached）归档为 A18 已冻结的比较数据，不再进入生产、回放与后续证据流程。申报书要求的"内联/共享函数/混合布局比较"由 A18 冻结记录满足。
2. 插桩不新增 import；保留数值索引；export/start/element 目标改写须有引用完整性测试（A01/A06 等价口径见第 4 节）。
3. manifest 最小化：记录费用模型版本、布局、配置、输入/输出哈希与确定性声明；sidecar 不再保存逐条 site 表——`instrument verify` 从实际 Wasm 的 guard 序列重建 span 表核对（现行实现已具备该能力）。
4. 同输入/配置/版本输出同一产物；不完整产物无有效 manifest。

## 3. 体积预算（规范正文）

申报书 v2 的体积门槛为：原件至少 10 KiB 的代表模块，插桩后体积 ≤ 原件 3×；原件小于 10 KiB 的代表模块，新增体积 ≤ 15 KiB；sidecar 单列不隐藏。

**规范性削减清单（全部为 A19 服务）：**

| # | 削减项 | 预期收益 |
| --- | --- | --- |
| 1 | 删除 span 内逐指令回放（profile 57 位权重编码、余额传参） | 每省 ~10 B；F1 约 −8 KiB（780 guard） |
| 2 | 直线合并不设上限 | 直线/展开段 guard 数大幅下降（F3 最显著） |
| 3 | 冷路径统一共享失败 helper（site 常量 + call） | 每省冷分支 ~5–9 B |
| 4 | 栈支配检查复用（F1 站点 267→84 已实测） | 栈检查字节约 −70% |
| 5 | manifest/sidecar 最小化 | 产物外附带体积 −95% 以上 |

**已知风险（历史记录）：** v4 初版曾以 2× 和 10 KiB 新增作为体积门槛，并据此记录 F1/F2 的算术下限风险。申报书 v2 已将门槛更新为本节所列 3× 和 15 KiB。S49 已用独立 holdout 重判 A19 为 PASS，A17 为 FAIL；调优数据不替代正式结果，详见 [S49](evidence/S49.md)。验收脚本及诊断脚本使用同一门槛函数，避免历史计算公式影响当前结果。

## 4. 精简验收（从申报书推导）

### 语料与正确性

出处：申报书"差分与验证"段。

1. ≥60 个具名确定性用例，其中 ≥20 个控制流/栈边界用例，覆盖 ≥3 类真实 MoonBit 工作负载（F0/F1/F2/F3 及同类认证输入）。
2. ≥10,000 个不同有效生成/变异样本，实际插桩并执行/受控 trap；记录种子；最小失败样例进回归集。
3. 独立计费预言机（不复用生产分析器）；手算轨迹与预扣语义一致。
4. 拒绝路径每类有边界用例：全部 SIMD、禁用指令/类型、可变 funcref table、重复插桩、未知模型、格式损坏、输入上限。

### 双引擎差分

出处：申报书"跨运行时证据"段。

- 同一份产物在 wasmoon 与 Wasmtime 实际执行；预算充足时原/插桩返回值、输出、选定内存状态一致；
- 受控终止比较 code/site 及输出前缀；原生 trap 分类单列；不用"能加载"替代执行验证；
- NaN、WASI、底层分配差异单列，不伪造一致。

### 性能门槛（维持不动）

出处：申报书"性能与体积"段。

- 各引擎、各适用计时窗口：完整保护时间比几何平均 ≤2×（95% CI 上界判定）；逐负载中位数及 p95 ≤3×；
- 生命周期窗口含实例化与 core start 业务；适用负载另测热调用；Fuel-only 数据单列；
- 只对代表应用判定 A17/A19，微基准用于诊断。先在调优集确定布局并冻结候选与输入配置，独立 holdout 只确认达标。调优结果不写入最终判定。
- 内部统计协议采用 1 万次配对整进程 bootstrap，整组保留进程内时间序列。调优每单元 3 进程，独立验收按固定 20 进程执行，各进程 300 样本并保留全部成功观测。按区间上界判定，独立验收禁止看到区间后再增加样本。

### 构建与体积门槛

体积门槛和构建、内存报告来自申报书。构建工程预算来自 S20。

- 体积：见第 3 节；
- 构建工程诊断：三档规模（64 KiB / 512 KiB / 4 MiB），记录 S20 的最大输入 10 s / 512 MiB 预算。A20 与历史跨版本回退规则不参与申报书的 A17/A19 最终判定。

### 演示（验收产物）

出处：申报书"资源控制演示"段：长短循环体费用差异、有限计算加 Fuel 完成、无限循环有限 Fuel 终止、深递归与浅调用大栈帧分别受控、memory/table 初始及增长边界、预算充足结果一致、受控失败带原因与原始位置并与程序自身 trap 区分。

### 状态判定

只有 PASS / FAIL / BLOCKED / NOT_RUN；每项有独立用例 ID、命令、退出码、产物哈希与复现环境；申报材料可使用阶段结果但须标明尚未生产验收。
