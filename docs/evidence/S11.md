# S11 调用前栈预算与入口包装验收

执行日期为 2026-11-16，Git 基线为 `b6a4783`，使用当前工作区。验收范围为 docs/07 S11 中 A05–A08 的插桩部分。

## 改写与成本归属

- `production-v1` 同时提供 `--max-stack-units` 和 `--max-call-depth` 时启用 StackPass。两值为正 i64，预算 global 保持私有。`--stack-layout` 打印最终生成代码的逐函数 A、C 和辅助帧归属。
- 直接调用先执行源调用点的静态 Fuel，再检查并预留被调函数的 `C` 和一层深度。两项都通过才扣减，正常返回时归还。归还序列让原有返回值留在操作数栈上。Stack 失败写诊断 code 4，Depth 失败写 code 5，两者复用原调用点 site。
- export 和 start 使用原签名 wrapper。同目标的导出别名与 start 共享 wrapper。固定 funcref 表的活动元素指向追加的间接 wrapper。间接签名追加一个 i32 site，原 `call_indirect` 仍由引擎检查索引、空槽和类型，目标有效后才检查预算。入口和间接 wrapper 内调用原索引。生成 Growth helper 的运行成本归入调用者 A，不产生第二次逻辑预留。
- 模块保留原 import 和原函数、类型、global 索引。最终产物独立验证前，管线按 `stack-v1` 对每个生成布局检查 A ≤ C。外部 wrapper 自身入口需要引擎余量，间接 wrapper 存活成本计入发出间接调用的原函数。

## 验收结果

| 条款 | 两套引擎的实测结果 |
| --- | --- |
| A05 | 128 个 v128 local 的叶函数 C=395，调用者 C=139。预算 534、深度 2 返回 `(42, 7)`。栈少 1 时 code 4，深度少 1 时 code 5，均在 site 6。同时不足时 code 4。互递归每帧 96 个 v128 local，17 层在 5,627 单位下返回 `(77, 88)`。把预算减至 5,626 并传入 4,096，先收到 code 4、site 21，无引擎原生栈溢出。 |
| A06 | 验证直接调用、提前 return、多返回值、别名 export、start、固定表和导入函数的直接调用／export／start／元素入口。间接调用保留 v128 参数和 `(v128, i64)` 返回值。核对函数索引列表、函数引用表达式、空值、表边界、原生类型不匹配和结构相等的重复类型。输出反汇编核对 import 及重写后的 export/start/element 目标。 |
| A07 | 所有生成布局满足 A ≤ C。直接用例的叶函数、调用者和导出 wrapper 分别为 `272/395`、`16/139`、`15/102`。间接调用者包含 16 单位活跃 wrapper，`A/C=34/142`。memory grow 调用者包含 17 单位 helper，`A/C=31/141`，逻辑深度 1 时连续两次 grow 返回 1、2。低 Fuel 先于直接栈检查和间接无效索引，export 先于源函数的 Fuel。无效间接目标维持原生 trap，诊断为 `0/0`。 |
| A08 | 同一实例在精确栈预算及深度下调用 `run` 和 `alias`，均返回预期值。Fuel 14 累计消耗，第三次调用在 site 5 收到 code 1。测试只读取陷阱诊断 global，之后结束实例。start 失败由引擎报告初始化 trap，实例诊断不可用。产品 runner 的实例废弃、拒绝复用和重入由 S13 验收。 |

锁定的 F0 `hello`、F2 `lisp_eval`、F3 `sha256_hash` 均通过独立校验并与原始预期输出一致。F2 在 100,000 单位、深度 128 时触发 code 5（site 594），把深度提高到 512 时触发 code 4（site 667）。两套引擎回溯指向 Wasm 偏移 `0x4bda` 和 `0x5519`，`wasm-tools dump` 核对了两个诊断分支。最终 F2 用 500,000 单位和深度 2,048，F0、F3 用 100,000 单位和深度 128。F1 `json_parse` 的 production-v1 输入冲突见 [S09](S09.md)。

这些预算属于各自的测试用例。S03 的同形探针记录原生栈余量，S11 的真实生成代码压力用例验证受测配置下的受控失败。生产上限及运行器强制执行仍需后续验收。[S03 栈余量](S03.md)

## 复现

在已按 S02 配置的 Linux x86_64 环境，从仓库根目录运行。实测为 Ubuntu 24.04 WSL2、glibc 2.39，软硬线程栈限制均为 8,192 KiB。wasmoon 0.18.0 和 Wasmtime 50.0.0 执行同一批 Wasm 和 WAST。Wasmtime 显式使用 `max-wasm-stack=524288`，独立校验器为 wasm-tools 1.263.0，Linux MoonBit 为 0.1.20261104（940aa18）。

```bash
export LC_ALL=C
ulimit -s 8192
mkdir -p _build/s11-stack
python3 integration/stack_pass/check.py > _build/s11-stack/run.log 2>&1
python3 integration/policy/check.py > _build/s11-stack/policy-regression.log 2>&1
```

主矩阵中 wasmoon 与 Wasmtime 各运行 32 个用例，均退出 0。wasm-tools 独立校验 36 个模块，全部通过，其中 29 个为插桩产物。缺少一项预算、深度为零和 legacy 搭配栈预算均明确拒绝，退出 2，且未产生文件。S09 策略和 S10 布局回归退出 0。

在 Windows PowerShell 7 使用 MoonBit 0.1.20261016（1af328f）执行 `moon info`、`moon fmt`、`moon fmt --check`、`moon check --target wasm --deny-warn` 和 `moon test --target wasm`，指定 `--target-dir _build/s11-pwsh`。MoonBit 测试 80/80，`python -m unittest discover -s integration/fuel_oracle` 9/9，`git diff --check` 退出 0。
