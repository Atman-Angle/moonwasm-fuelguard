# S15 可恢复文件交付验收

执行日期为 2026-11-17。Git 基线是 `b6a4783`，测试使用包含 S01–S14 实现的工作区。验收依据为 [任务分片 S15](../07_任务分片_MoonWasm_Instrument.md) 和 [验证计划 A21](../09_验证与验收计划.md)。

## 结果

| A21 验收项 | 实测结果 |
| --- | --- |
| 已有目标及路径别名 | Windows NTFS 和 Linux ext4 均拒绝覆盖已有 Wasm、报告、自身输入或其硬链接，源文件及哨兵 SHA-256 不变。Linux 拒绝悬空软链接、目录软链接和 bind mount 的目标别名。Windows 拒绝大小写别名及可能与同目录另一个新目标重叠的 8.3 短名。两端均拒绝经过 `..` 的目标与报告路径冲突。 |
| 并发发布 | 两个真实 CLI 进程用不同 Fuel 预算争用同一对输出。两端均只有一个退出 0，另一个退出 2。最终 manifest 的预算与胜者一致，Wasm 摘要匹配，临时文件清理完毕。白盒用例在发布 manifest 前注入并发文件创建，冲突文件字节不变，已发布的 Wasm 保留，消费者拒绝该组合。 |
| 权限失败 | Linux `setpriv` 以 UID/GID 65534 运行 CLI。Wasm 目标目录可写，报告目录权限为 `0555`。实际系统调用返回 `EACCES`，两份最终文件均未发布，输入未变。 |
| 磁盘满 | 在独立 Linux mount namespace 中挂载 4 KiB tmpfs，分别让 Wasm 和报告写入该文件系统。两次均发生真实 `ENOSPC`，两个最终路径都没有发布，所有本次临时文件均已清理。 |
| 部分写与校验失败 | 白盒用例通过实际文件句柄只写入报告前两个字节后注入错误。未发布 Wasm 或 manifest，使用同一对路径重试成功。等长内容损坏在临时文件校验阶段退出。故障注入在 Wasm 发布后改变其字节，最终路径校验拒绝发布 manifest。替换暂存目录入口的普通文件保持原字节。 |
| 消费者 | `instrument verify … --report …` 对完整配对退出 0。对缺失 Wasm、缺失报告、FIFO、截断 JSON、缺少 codegen 或包含无效 pass 的 manifest、摘要不匹配的 Wasm，均退出 2。输入文件名为 `verify` 的原 CLI 用法仍成功。 |

## 环境与能力边界

Windows PowerShell 7 使用 MoonBit `0.1.20261016 (1af328f)`。Linux 为 Ubuntu 24.04 WSL2，使用 MoonBit `0.1.20261104 (940aa18)`。两端均运行 `--target wasm`，文件层声明 `moonbitlang/async@0.22.4`。Linux 端以 WSL 原生文件系统上的隔离源码副本验证。Wasm 插桩内核保持独立于运行引擎。

在两个锁定的 Moonrun 版本里，导入 WASI `path_link`、`path_filestat_get` 或 `fd_sync` 的单函数探针均出现缺失导入。实际交付使用已实测的异步文件 API。WSL 的 `/mnt/d` DrvFS 对 `rename(replace=false)` 返回 `EINVAL`。CLI 退出 2，两个最终目标与临时文件均不存在，已有源文件及哨兵摘要相同。该挂载点的发布明确受限。[Moonrun 的平台重命名实现](https://github.com/moonbitlang/moon/blob/940aa18/crates/moonrun/src/filesystem/os.rs)

## 复现

在 Windows PowerShell 中执行。

```powershell
moon info --target wasm --target-dir _build/s15-pwsh
moon fmt --target-dir _build/s15-pwsh
moon fmt --check --target-dir _build/s15-pwsh
moon check --target wasm --deny-warn --target-dir _build/s15-pwsh
moon test --target wasm --target-dir _build/s15-pwsh
python -B integration/delivery/check.py
git diff --check
```

在 Linux 原生文件系统的工作副本中执行。`--os-failures` 阶段使用 root、`setpriv` 和私有 mount namespace。为 S14 回归将锁定的 wasm-tools、Wasmtime 和 wasmoon 加入 `PATH`。

```bash
moon test --target wasm --target-dir _build/s15-tests
unshare --mount python3 -B integration/delivery/check.py --os-failures
python3 -B integration/manifest/check.py
bash scripts/check-cli-failures.sh
bash scripts/check-e2e.sh
```

Windows 和 Linux Wasm 单测均为 90/90，独立计费预言机 9/9。两个平台的发布集成脚本和 Linux 的真实故障用例通过。S14 的双引擎映射回归、既有 CLI 失败路径和 hello 端到端回归均通过。

## 独立代码审查

子代理使用 `check` 审查并复现反例，主代理修复后复验。

| 严重程度 | 发现与处理 |
| --- | --- |
| P1 | 公开暂存路径可能被替换，造成错误发布或清理不属于本次的文件。改为目标目录内的私有随机子目录，限制清理范围，并在发布 manifest 前读回最终 Wasm。 |
| P2 | 同目录的 Windows 8.3 别名可能在首个发布后才出现。增加短名冲突预检。消费者曾接受缺字段的 JSON，也会在 FIFO 上阻塞。增加结构、pass 和普通文件检查。 |
| P3 | `verify` 子命令与原先同名输入冲突。带 `-o` 的原用法继续走插桩。 |

修复复核在受信任的目标目录模型内没有发现新增必修项。验证针对命令执行期间的故障和冲突。目标目录及其祖先的 ACL、进程强制终止以及校验到实际使用之间的文件变化见 [交付契约](../implementation/manifest-v1.md#交付与校验)。
