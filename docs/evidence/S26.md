# S26 · fuel-v1.2 合并计费块与性能试点

本页记录原始 S26 试点。后续独立缓存布局与冻结基线的对照见
[F1 性能攻坚](Fuel-optimization.md)。

执行日期 2026-11-19（北京时间）。分支 `feat/s26-join-span`，基线
`c2a7d16`。S20 的布局实现来自 `f3492f5`，S25 的 SIMD-free 语料来自
`c2a7d16`。验收依据为 [任务计划 S26](../07_任务分片_MoonWasm_Instrument.md#s26-fuel-v12合并计费块划分与性能试点m1)。

## 实现与复核

[fuel-v1.2 边界表](../implementation/fuel-v1.2.md)定义 join-span 起点、
19 条计费指令上限、权重打包、i64 符号判据及迁移方式。完整候选通过
`--cost-model fuel-v1.2 --codegen join-span` 选取。源指令站点与原模型
一致，静态扣费为 8 条热路径指令，共用一个冷路径 helper。独立编码
校验与管线的 `A ≤ C` 检查覆盖试点全部插桩产物。

独立子代理按 `/check` 做只读对抗性审查。两项 P2 均经主代理修复并由
子代理复验。唯一落穿的显式 else 现在可与后续连续指令同段。预算为 5
的反例在站点 7 陷阱时保持全局量原值。有第二个出口前驱的对照仍切分。
CLI 现在拒绝空表覆盖非空指令站点的清单。复核还执行了混合权重回放、
跨 i64 符号位的 profile、嵌套 `br_table`、循环回边、动态费用及调用点
Depth 诊断的反例。子代理另行复核了清单元数据修正。

## 冻结环境与语料

使用 `FuelGuard-S26` 的 Ubuntu 24.04.3 WSL2 与 S18 同一台 Core Ultra 9
185H。内核 `6.6.114.1-microsoft-standard-WSL2`，glibc 2.39，GCC 13.3.0，
Windows build 26300，交流电和平衡电源模式，串行绑定 vCPU 4。恢复的 MoonBit
`0.1.20261104 (940aa18)` 和 core 归档经过 [S02 摘要](S02.md)复核。
Wasmoon 0.18.0，Wasmtime 50.0.0 官方 C API，独立验证器 wasm-tools 1.263.0。

首轮尝试在计时前发现新语料的 `core_start` 元数据继承了旧值。F1、F2
和两个对应保留样本的实际 Wasm 均没有 start section。修正四个布尔字段后，
清单 SHA-256 从 `480f49811c5cf2a43262ce2e9aebb0198aecf0d9a360942a44880a8ed830fc45`
变为 `ada027679aaab88d850b33e7129b5b5b9fbbcff2b2bc2e8316560b547aca8836`。
全部 11 个非构建文件的大小、SHA-256 和实际 start section 经独立核对。
F3 和 start-only 微基准仍包含 core start。保留集只做静态核验。
F0–F3 和两个调优微基准以种子 `180026` 交错运行三个布局。每组每变体
5 次预热、30 次计时、每组独立进程，共三组。回放种子为 `180027`。

```bash
export MOON_HOME=/root/s26-frozen-moon
export PATH="$MOON_HOME/bin:/opt/fuelguard-s26/bin:/usr/bin:/bin"

python3 -B bench/run.py --compare-join-span --out _build/s26-pilot-final \

```

## 正式试点结果

**S26 BLOCKED。** F1 wasmoon 热调用的中位数为原版的 **3.285×**，
95% 配对 bootstrap 区间为 **[3.091×, 3.431×]**。原版、`p2-prefix` 和
`join-span` 的中位数分别为 2.726、10.505 和 8.956 ms。候选相对
`p2-prefix` 缩短 14.7%，仍高于 2.2× 验收线并触发 2.5× 停止线。

## 热路径密度

| 用例 | 源计费指令 | 静态 span | 平均长度 | 长度 1–5 | 长度 19 |
| --- | ---: | ---: | ---: | ---: | ---: |
| F0 | 2,399 | 346 | 6.93 | 198 | 42 |
| F1 | 5,054 | 780 | 6.48 | 517 | 93 |
| F2 | 4,129 | 623 | 6.63 | 373 | 79 |
| F3 | 4,348 | 500 | 8.70 | 241 | 125 |

对 F1 候选的副本，在经反汇编确认的 780 个扣费入口各加一个计数器。
用 Node WASI 执行一次 `_start` 并核对原有 `checksum=8928400`。
动态执行 2,800,050 次 span 扣费，覆盖 17,058,295 条源计费指令，平均
每次扣费覆盖 6.09 条。长度为 4 的 span 有 1,274,692 次，长度 1–5
合计占 76.9%，长度上限 19 的 span 占 8.8%。因此长度上限只能解释一部分
开销。核心解析循环及高频短函数仍执行大量短 span。

| F1 源函数索引 | 源计费指令 | 静态 span | loop / 条件分支指令 | 扣费执行次数 | 动态平均长度 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 42 | 351 | 60 | 3 / 20 | 718,200 | 6.05 |
| 22 | 10 | 4 | 0 / 2 | 447,200 | 4.00 |
| 17 | 4 | 1 | 0 / 0 | 445,602 | 4.00 |
| 41 | 44 | 19 | 0 / 7 | 262,000 | 2.87 |
| 39 | 177 | 24 | 1 / 7 | 227,200 | 10.60 |

前四个函数贡献了 66.9% 的扣费执行。函数 42 覆盖了三个 loop 和 20 条
`if`／`br_if`／`br_table`。函数 17 虽只有一个四指令 span，仍随高频
调用重复扣费。完整直方图和逐函数静态分布见 `report.json`，动态计数见
`F1-hot-density.json`，可运行 `python -B _build/s26-evidence/probe-density.py`
复跑。计数副本只用于归因，正式计时使用原始候选。
