## 0. 执行摘要

### 0.1 一句话结论

**MoonBit 生态已经不缺“库的类别”，缺的是“能被真实项目用起来的标准输入、集成层和工程质量”。**  
因此本次调研淘汰了绝大多数“再实现一个 X”的方向，首选一个把行业标准 OpenAPI 接进 MoonBit 服务端工具链的项目：**oas2server（OpenAPI 3.x → MoonBit 类型化服务端脚手架）**。

### 0.2 排序后的候选

| 排名 | 项目 | 一句话定位 | 综合判断 |
|---|---|---|---|
| 1 | **oas2server** | 把 OpenAPI 3.0/3.1 规格生成可编译的 MoonBit `moonapi` 服务端：类型模型、描述符、路由、handler 骨架、校验与 OpenAPI 回吐 | **推荐作为首选**。外部需求验证充分、MoonBit 侧缺口明确、与你已有 OpenAPI 经验高度契合、一个月可交付垂直切片 |
| 2 | **moonquery** | 纯 MoonBit 的 SQLite 文件 SQL 查询引擎：在 WASM/原生/JS 上直接对 `.db` 文件做只读分析查询 | **高上限、高风险备选**。MoonBit 结构性优势最强（纯实现、全后端、无 FFI），但 WAL、SQL 语义与一个月工期是硬约束 |
| 3 | **mooncert** | MoonBit 包兼容性与质量门禁：跨 target/跨工具链构建测试、API 兼容、文档示例、覆盖率、许可证，一键出报告/徽章 | **条件备选，不作为首选**。生态痛点真实、技术风险低，但靠近官方工具领地，且技术纵深较浅；需先向包作者与官方验证 |

**严格来说，只有前两个达到“值得立项”的门槛；第 3 个是条件备选，不建议为了凑数而做。** 如果前两个的需求验证都失败，更理性的选择是把 OpenAPI import 贡献给 mctl（维护赛道），而不是硬推第三个项目。

> 名称可用性：截至 2026-10-31，`oas2server`、`moonquery`、`mooncert` 在 mooncakes 上均未发现同名模块；发布前应再次核对（mooncakes 的命名规则与保留名可能变化）。

### 0.3 明确不建议的方向

- **再写 HTTP 服务器/框架、MQTT/Kafka/NATS 客户端、任务队列、YAML/TOML 解析器、PDF/Office 工具链、DataFrame/Arrow、向量库客户端、MCP SDK、WASM 运行时、正则引擎、JWT/OAuth、OTel**：这些方向在 2026-10 的 MoonBit 生态中已经有一个或多个实现，部分由官方团队直接维护。详见第 5 节淘汰记录。
- **纯 AI/Agent 应用**：不是不能做，而是外部（TypeScript/Python）已有大量成熟方案，MoonBit 侧也已有 MCP SDK、Agent 框架、工作流引擎。除非能说清“为什么必须是 MoonBit”，否则不建议把宝押在“又一个 Agent 工具”上。
- **只做应用、不沉淀可复用核心**：赛事评审看“真实可用”，但长期价值来自可复用组件；纯应用在季度评选中容易被当作示例工程。

## 2. 调研方法与判断标准

### 2.1 第一性原理

对每个方向，先回答六个问题，而不是先看“有没有包”：

1. **谁**在什么场景下有痛点？（具体角色，不是“开发者”）
2. 他们**现在怎么做**？（现有工具/绕路/手工）
3. 现有方案**哪里不够**？（价格、性能、部署、类型安全、集成成本、许可证）
4. 为什么**必须是 MoonBit**？（全后端、WASM、无 FFI、小体积、类型系统、工具链）
5. 我们能在**一个月**内交付什么可验证的核心？
6. 交付后**谁会用**、凭什么持续维护？

### 2.2 证据分级

本报告对关键结论标注：

- `[已验证-一手]`：官方文档、官方仓库、mooncakes API、我本地编译/运行结果。
- `[已验证-描述级]`：mooncakes 模块的名称/版本/描述/关键词；未逐行审计源码。
- `[推断]`：基于多条证据的合理判断，但未直接验证。
- `[未知]`：明确没有证据，或无法在本环境验证。

**重要**：mooncakes 上“存在一个包”不等于“这个包可用”。本次只对少数关键竞品做了源码/README/本地运行级复核；淘汰记录中标注“描述级”的方向，若你日后想回头做，必须先做代码级审计。

### 2.3 对抗性审查清单

每个候选都要通过以下反例测试：

- **反例 1：外部已有成熟工具，MoonBit 用户直接调用即可。** 例如 OpenAPI→MCP 已有 900+ stars 的 TS 实现；再写一个 MoonBit 版，优势必须具体。
- **反例 2：官方团队已经在做。** 例如 PDF（pdflite）、Office（office-lib/mbtexcel）、WASM 运行时（wasm5）、WASM Component（官方博客/示例）、Agent（openseek/workflow）。与官方正面竞争，除非质量绝对领先，否则不建议。
- **反例 3：需求是“我想做”，不是“别人需要”。** 例如“又一个解析器”“又一个游戏”。
- **反例 4：一个月只能做出玩具版。** 例如完整 SQLite 引擎、PDF 渲染器、HTTP/3、浏览器引擎。
- **反例 5：没有分发/采用路径。** 做完没人安装、没人依赖，长期价值为零。
- **反例 6：许可证/来源不清。** 移植项目必须核对原项目许可证；参考代码必须注明范围。

### 2.4 奥卡姆剃刀

在能证明价值的前提下，选**最小可验证切片**：

- 不做完整 OpenAPI，先做“最常用 80% 的 OpenAPI 子集 + 明确拒绝其余”。
- 不做完整 SQLite，先做“只读 SELECT 子集 + 明确不支持 WAL/写入”。
- 不做完整质量平台，先做“一个仓库、一条命令、一个 CI Action”。

### 2.5 调研过程与核验深度

**数据来源与步骤**

1. **全量模块清单**：抓取 mooncakes `modules` API 的 3,498 条模块记录，按名称/描述/关键词做领域分布、创建时间、版本号统计（附录 A）。
2. **依赖与版本**：对关键包调用 `manifest` API，读取 `latest_version`、`dependents`、`repository`、`deps`，判断维护状态与生态位。
3. **GitHub 组织**：拉取 `moonbitlang`、`moonbit-community` 等组织仓库，核对 stars、最近推送时间、描述；对外部竞品（openapi-generator、oapi-codegen、MCP 等）取 stars 作为需求证据。
4. **官方路线**：阅读 MoonBit 官方博客（Agent、SeekMoon、属性测试、WASM Components 等）与官网，提取官方优先级。
5. **源码级/README 级核验**：对约 15 个关键包做 README/API/源码/本地运行核验，避免“只看名字”判断重复或缺口（见下表）。
6. **本地编译 spike**：用 MoonBit 0.1.20261016 在 Windows 原生验证 moonapi 服务端、校验、OpenAPI 回环；验证 moon-lite 读 SQLite；记录版本坑（第 7 节）。
7. **对抗性审查**：对每个候选问“外部是否已有成熟方案”“官方是否在做”“一个月能否交付”“谁会用”，淘汰不成立的方向（第 5、11 节）。

## 4. 重新定义“生态缺口”

### 4.1 三个常见的错误论证

1. **“mooncakes 没有 X，所以需要 X。”**  
   反例：OpenAPI→MCP 在 MoonBit 没有，但外部有 900+ stars 的 TS 实现，MoonBit 用户可以直接跑 Node 版；除非你能给出“必须是 MoonBit”的结构性优势，否则这不是需求。
2. **“官方推荐清单里有 X，所以我做 X。”**  
   反例：官方推荐的 HTTP 服务器、MQTT、Kafka、NATS、向量库客户端、Arrow/DataFrame 在 2026-10 都已有实现；推荐清单是方向，不是空白。
3. **“竞品很弱，所以我能赢。”**  
   反例：竞品可能弱，但用户迁移成本高、生态惯性大；而且很多“弱竞品”是官方/半官方维护，质量和维护者注意力都比你强。

### 4.2 本报告采用的缺口定义

一个方向值得立项，必须同时满足：

1. **有可指认的用户与 workflow**：不是“开发者可能需要”，而是“某类人在某件事上现在必须手工做/绕路/放弃”。
2. **现有 MoonBit 方案不可用或明显不足**：不是“没有”，而是“有但缺少关键能力/质量/集成”。
3. **MoonBit 提供结构性优势**：全后端、WASM、无 FFI、小体积、类型安全、编译期校验、工具链一体化中的至少一项。
4. **一个月能做出可验证的核心**：有明确的 MVP 边界和“不做清单”。
5. **有采用路径**：能接进现有框架/工具链/CI，或有明确的早期用户。
6. **有长期维护理由**：标准稳定、用户会持续用、你能持续迭代。

### 4.3 由此得到的三个“真缺口”

| 缺口 | 为什么是真缺口 | 为什么现在可做 |
|---|---|---|
| **OpenAPI → MoonBit 服务端** | MoonBit 有代码优先框架（moonapi）、有 `.api` DSL 生成器（mctl）、有你已有的 OpenAPI 客户端生成器（oas2moon），但没有把行业标准 OpenAPI 接进服务端；现有 mctl 要求重写规格 | moonapi 的描述符/校验/OpenAPI 回吐已成熟；你的 oas2moon 已证明 OpenAPI 前端可行；本地已验证 Windows 原生服务端可跑 |
| **纯 MoonBit 的 SQLite 查询引擎** | 有多个纯只读文件解析器（moon-lite、moonsqlitefile、pagelens），但没有 SQL 执行器；native/JS 绑定很多，纯实现为零 | moon-lite 已解决 b-tree/record 解码；sqlparser 已提供 SQL AST；本地已验证纯 MoonBit 读 SQLite 可行 |
| **MoonBit 包兼容性/质量门禁** | 3,498 模块、单月 1,291 新增、工具链高频变更，包作者缺少一条命令的跨 target/跨版本质量门禁；现有工具碎片化 | 现有 mooncompat/mooncov/harborcheck/mooncram 等可复用；CLI + CI Action 一个月可做 |

**注意**：第三个缺口虽然真实，但“官方可能自己会做”，且技术纵深不如前两个；因此列为条件备选，不作为首选。

| 50 | 容器/K8s/云原生 | `kubemoon`、`docker`/OCI 工具、`moonproxy` | 淘汰（或过早） | 有早期实现；K8s 客户端工程量大，需求未验证 |

### 5.2 重点淘汰说明

#### 5.2.1 为什么不选 HTTP/Web 框架

`moonbitlang/async/http` 提供 HTTP 客户端/服务端，`moonbitstack/mooncat` 是 ASGI 服务器，`moonapi` 是类型化框架，`moonback`/`crescent`/`moonzero` 是不同风格的 Web 框架，`rabbita` 是前端 UI 框架。再加上 `moonhttp` 的 HTTP/1-3 格式层、`moonrpc` 的 gRPC，HTTP 栈已经非常拥挤。

`[已验证-一手，README/API]`

在这些之上再做一个框架，除非你在 DX、性能或类型安全上有数量级优势，否则评审很容易问：“为什么不用 moonapi/moonback？”这不是一个好问题。

#### 5.2.2 为什么不选 YAML/TOML/PDF/Office/DataFrame

这些都是“看起来缺，实际已有很多”的典型：

- YAML：`bobzhang/yaml` 明确目标 YAML 1.2，带 `yamlsuite` CLI 和 yaml-test-suite 脚本；`moonyaml` 支持 1.0/1.1/1.2、保留注释/锚点/标签的无损文档；`moonbit-community/yaml` 是简化子集。[bobzhang/yaml](https://mooncakes.io/docs/bobzhang/yaml)、[moonyaml](https://mooncakes.io/docs/moonbitstack/moonyaml)
- PDF/Office：官方 `pdflite` + `pdf2md`，`office-lib` + `mbtexcel`（300+ 公式）+ `pptx`，`typst` 端口。[pdflite](https://mooncakes.io/docs/moonbitlang/pdflite)、[mbtexcel](https://mooncakes.io/docs/moonbitlang/mbtexcel)
- DataFrame：`MoonFrame`、`pandas`、`moonlake`（SQL over CSV/Parquet, WASM）、`arrow`、`parquet`、`colenc`。[moonlake](https://mooncakes.io/docs/superbigcup325/moonlake)

如果你在这些方向没有“数量级更好”的把握，不建议用一个月去重复。

#### 5.2.3 为什么不选 MCP/Agent 沙箱

MCP SDK 侧：`moonmcp` 已支持 tools/resources/prompts、stdio + Streamable HTTP、双协议时代；`marianoguerra/mcp` 提供协议类型/JSON-RPC/header 校验；`peter-jerry-ye/mcp-server`、`mcpbox` 等也在。

Agent 沙箱侧：`aegisrun` 定位就是 “AI Agent Secure Tool Runtime (MoonBit + Wasm)”；`moonrockz/extism` 是 Extism host；`moonjail` 做 Linux 最小权限沙箱；`wasmoon`/`wasm5` 提供 WASM 运行时。官方博客也把“跨 OS 一致的 WASM 沙箱”作为 MoonBit Agent 能力。

`[已验证-描述级/README]`

结论：这个方向不是没有需求，而是**已经有一圈占位者，且安全正确性极难在一个月内证明**。除非你能做出明确的差异（例如可审计的能力策略、确定性回放、MCP 一致性测试），否则不建议。

#### 5.2.4 为什么不选“纯 OpenAPI → MCP 网关”

外部需求确实大（MCP servers 91k stars，openapi-mcp 900+/600+ stars），但：

- 外部已有多个成熟 TS/Python 实现；MoonBit 用户可以直接运行 Node/Python 网关。
- MoonBit 侧已有 MCP SDK；缺的只是 OpenAPI 映射层，工程量不足以支撑一个独立旗舰项目。
- 它和 oas2server 共用 OpenAPI 前端；更适合作为 oas2server 的 **可选输出**（`--mcp`），而不是另起炉灶。

#### 5.2.5 为什么不选“再做一个 SQLite 绑定/读取器”

绑定已经很多：`moonbitstack/moonsqlite`（native FFI）、`moonbit-community/sqlite3`、`KKKIIO/sqlite`（native 或 node:sqlite）、`mizchi/sqlite` 等；纯读取也有 `moon-lite`、`moonsqlitefile`、`pagelens`。

`[已验证-描述级]`

缺的不是“读文件”，而是 **SQL 执行器** 和 **纯实现写入**。这才是候选 2 的切入点；如果只做又一个读取器，价值不足。

> 排序依据：风险调整后的综合价值 = 需求真实性 × 生态缺口 × MoonBit 结构性优势 × 一个月可交付性 × 采用路径 × 长期维护价值。  
> 三个项目都给出“做什么/不做什么/怎么验证/怎么验收”，但只有第 1 个是明确推荐；第 2 个是高上限备选；第 3 个是条件备选。

### 6.1 候选 1（推荐）：oas2server — OpenAPI 3.x → MoonBit 类型化服务端脚手架

#### 6.1.1 一句话定位

**把一份 OpenAPI 3.0/3.1 规格，生成一个可编译、可运行、带请求校验和 OpenAPI 回吐的 MoonBit 服务端工程；让 MoonBit 团队在不重写规格的前提下采用契约优先（contract-first）后端开发。**

它不是“又一个 Web 框架”，而是 **标准输入 → MoonBit 代码** 的生成器，运行时复用 `moonapi`/`mooncat`/`async`。

#### 6.1.2 三个完整使用场景

**场景 A：已有 OpenAPI 契约的 API 团队**

- 一个团队已经有了 `openapi.yaml`（3.1），描述了用户、订单、支付等 30+ 个端点；他们想用 MoonBit 写服务端。
- 今天的选择：手写 `moonapi` 路由和模型（重复、易漂移），或者用 mctl 把规格重写成 `.api` DSL（额外维护一份规格）。
- 用 oas2server：`oas2server generate openapi.yaml -o server/`，得到类型模型、路由、描述符、handler 骨架和 `main.mbt`；团队只需要实现业务 handler。生成的 `/openapi.json` 可以与原规格做机器对比，防止漂移。
- 价值：**规格是唯一事实来源**；类型、校验、文档三者不漂移。

**场景 B：MoonBit 后端团队对接外部 API**

- 团队要对接合作方的 OpenAPI（例如支付、物流、发票），需要在 MoonBit 侧实现一个兼容服务或 mock，供内部联调。
- 今天：手写模型/校验，或者用 Node/Python 生成器生成另一种语言的代码，再翻译。
- 用 oas2server：直接生成 MoonBit 服务端骨架 + 校验；未实现的 handler 返回 501，已实现的立刻可用于联调；生成的 OpenAPI 可交给前端/测试。
- 价值：**跨语言契约在 MoonBit 侧可用**，不需要先有 MoonBit 版 SDK。

**场景 C：Agent 原生 API**

- 团队有一个 REST API，想把它暴露成 MCP 工具给 Claude/Cursor/自研 Agent 使用。
- 今天：手写 MCP server 的 tool schema 和 HTTP 调用，容易与 API 漂移；或者用外部 TS/Python 网关。
- 用 oas2server（v1.1 可选）：同一份 OpenAPI 生成 MCP tool 定义 + 一个本地 MCP 网关，工具入参用 JSON Schema 校验，出参映射为 MCP content；HTTP 服务端和 MCP 工具共用同一套模型/校验。
- 价值：**一份规格，同时得到 REST 服务端、客户端 SDK（oas2moon）和 Agent 工具**。

#### 6.1.3 现有解决方案与竞品

| 方案 | 输入 | 输出 | 与 oas2server 的关系 |
|---|---|---|---|
| **moonbitstack/moonapi** 0.17.4 | MoonBit 代码（路由/描述符） | 可运行服务 + OpenAPI 3.1/3.0/2.0 文档 | **运行时与目标**；oas2server 生成它的代码 |
| **Lfan-ke/moonctl (mctl)** 0.7.1 | `.api` DSL（goctl 风格），另有 `.proto`/`.gql`/DDL/datasource | `moonapi` 脚手架、handler 骨架、OpenAPI 文档 | **最接近的竞品**；但输入是 MoonBit 自有 DSL，不是 OpenAPI |
| **Atman-Angle/oas2moon（作者前作）** 0.1.0 | OpenAPI 3.0.x JSON/YAML | 类型化 MoonBit **客户端 SDK** | **作者前作/可复用资产**；同一 OpenAPI 前端的另一个方向；MIT，可作为 oas2server 的前端依赖 |
| **OpenAPITools/openapi-generator** 26.8k stars | OpenAPI 2/3 | 多语言客户端/服务端/文档 | 成熟但无 MoonBit target；JVM 工具链；模板通用 |
| **oapi-codegen** 8.6k stars | OpenAPI 3 | Go 客户端/服务端 | Go 专用；证明“OpenAPI→服务端”是主流工作流 |
| **hey-api** 5.5k stars / **Speakeasy** | OpenAPI | TS SDK/validators/mocks | SDK 为主；非 MoonBit |
| **Smithy** 2.4k stars | Smithy IDL | 多语言客户端/服务端 | 另一种 IDL；MoonBit 侧有 `smithy-codegen-moonbit`，但与 OpenAPI 不互通 |

`[已验证-一手，README/API；star 数为 GitHub API 2026-10-31]`

**关键判断**：

- 外部“OpenAPI→服务端”是成熟工作流（openapi-generator、oapi-codegen 长期存在），需求不是伪需求。
- MoonBit 侧唯一接近的是 mctl，但它要求把 OpenAPI 重写成 `.api`；这对已有规格的团队是额外负担，而且 `.api` 的表达力弱于完整 OpenAPI/JSON Schema。
- MoonBit 侧没有“OpenAPI→服务端”的生成器（截至 2026-10-31 的 mooncakes 清单与 mctl 输入格式核对）。`[已验证-描述级；不能证明绝对不存在]`

#### 6.1.4 差异化与“为什么是 MoonBit”

1. **标准输入，而不是自有 DSL**  
   OpenAPI 是 API 团队的通用契约；支持它就降低了 MoonBit 的采用门槛。mctl 的 `.api` 适合“MoonBit 原生团队”，oas2server 适合“已有契约的团队/企业”。

2. **生成的是 `moonapi` 描述符，不是通用模板**  
   生成代码直接复用 moonapi 的：
   - 路由（`{id:int}`、`{rest:path}` 等）
   - 参数/请求体校验（FastAPI 风格 422，带 `loc`）
   - OpenAPI 3.1/3.0/2.0 回吐
   - ASGI 接口（可跑在 mooncat/native 或 WASM）
   这意味着生成器不需要自己实现运行时，质量下限由成熟的 moonapi 保证。

3. **类型安全 + 编译期检查**  
   生成的模型是 MoonBit `struct`/`enum` + `derive(ToJson, FromJson)`；handler 签名是类型化的；字段改名/类型变更会在编译期暴露，而不是运行时 500。

4. **全后端**  
   生成的服务端可以在 native 运行，也可以编译到 WASM（moonapi 支持 native/WASM）。这对边缘、Serverless、本地工具都有价值。

5. **一份规格，三个产物**  
   - 服务端：oas2server
   - 客户端 SDK：oas2moon（已有）
   - Agent 工具：oas2server `--mcp`（可选，v1.1）
   这是 mctl/openapi-generator 在 MoonBit 侧没有的组合。

6. **与你已有资产的协同（oas2moon 是你的前作）**  
   `oas2moon` 是你开发的 OpenAPI→客户端 SDK 生成器（MIT，仓库 2026-10-16 仍在更新）。本项目应直接复用/扩展 `oas2moon_frontend` 的解析与诊断，把新工作集中在 **服务端 IR + moonapi 代码生成 + 校验/回环测试** 上。这不是“和竞品互补”，而是“同一作者的前作延伸”；申报时必须披露，并说明新增工作。

#### 6.1.5 核心功能（MVP）

**输入**

- OpenAPI 3.0.x / 3.1.x，JSON 和 YAML。
- 支持：`paths`、`operations`（get/post/put/patch/delete）、`operationId`、`summary`、`description`、`tags`、`deprecated`。
- 参数：path/query/header/cookie；`required`、`schema`、`style`/`explode`（常用组合）。
- 请求体：`application/json`；`components/schemas`、`$ref`、对象/数组/枚举/基础类型、`required`、`nullable`、常用约束（min/max、minLength/maxLength、pattern、enum）。
- 响应：状态码、描述、JSON body schema；默认响应。
- 安全：`securitySchemes` 的声明（bearer/apiKey/basic/oauth2 的声明），生成 moonapi 的 security scheme 元数据；**不实现完整 OAuth2 流程**。
- 服务器：`servers` 的基础 URL（生成默认配置）。

**输出（生成一个 MoonBit 包）**

```text
server/
  moon.mod
  moon.pkg
  models.mbt        # struct/enum + derive(ToJson, FromJson) + T::schema()
  app.mbt           # App::new + 路由 + Endpoint/Param/ResponseSpec 描述符
  handlers.mbt      # 每个 operation 的类型化 handler 骨架（默认 501）
  main.mbt          # async fn main + mooncat.serve
  README.md
  tests/
    smoke_test.mbt  # 不启 socket，直接 app.handle 测试
```

**CLI**

- `oas2server generate <spec> -o <dir>`：生成工程。
- `oas2server check <spec>`：只做规格解析/支持度检查，输出诊断（JSON Pointer + 原因）。
- `oas2server diff <spec> <generated-openapi>`：把生成的 `/openapi.json` 与原规格做规范化对比，报告差异。
- `oas2server generate --mcp`（v1.1）：额外生成 `mcp.mbt` 工具注册（基于 moonmcp）。

**质量保障**

- Golden tests：固定输入 → 固定输出（格式化后逐字对比）。
- Compile tests：每个生成工程在 CI 中 `moon check` / `moon test`。
- Runtime tests：用 `app.handle` 直接发请求，断言状态码/JSON/422 结构。
- Round-trip tests：生成工程的 `/openapi.json` 与原规格对比（允许排序/描述等已知差异）。
- Corpus：Petstore、GitHub API 子集、Stripe 子集、至少 3 个真实公开规格。
- Diagnostics：不支持的 `oneOf/anyOf/allOf/discriminator`、callbacks、links、webhooks 等必须**显式报错/警告**，不能静默丢字段。

#### 6.1.6 明确不做（MVP 边界）

- 不实现 HTTP 服务器/路由/校验运行时（复用 moonapi/mooncat/async）。
- 不做数据库/ORM/迁移/认证实现。
- 不做完整 OpenAPI 3.1（先支持最常用子集；其余显式拒绝）。
- 不做 UI/管理后台/部署。
- 不做其他语言的代码生成。
- 不在 MVP 内实现 MCP 运行时（只预留 `--mcp` 输出；v1.1 再做）。
- 不做“自动实现业务逻辑”；handler 默认 501，业务由人写。

#### 6.1.7 技术路径

```text
OpenAPI (JSON/YAML)
   │
   ▼
[frontend] 解析 + 支持度校验 + JSON Pointer 诊断
   │
   ▼
[server IR]  规范化：Operation / Param / Body / Response / Security / Model
   │
   ├──► [codegen: models]    struct/enum + ToJson/FromJson + Schema
   ├──► [codegen: app]       App + Route + Endpoint/Param/ResponseSpec
   ├──► [codegen: handlers]  类型化 handler 骨架（501）
   └──► [codegen: main]      async main + mooncat.serve
   │
   ▼
生成的 MoonBit 工程
   │
   ├── moon check / moon test（CI）
   ├── app.handle 请求测试（无 socket）
   └── /openapi.json → diff 原规格（回环）
```

**实现要点**

- 前端：直接依赖 `oas2moon_frontend`（MIT，你的前作）解析 OpenAPI 3.0.x JSON/YAML；如果 3.1 支持不足，扩展它而不是重写。YAML 可用 `bobzhang/yaml` 或 `moonbitstack/moonyaml`；服务端 IR 需要新设计（客户端 IR 不含 responses/security/descriptor）。
- IR：把 OpenAPI 的 `$ref` 解析成稳定 ID；处理命名冲突（operationId 缺失时用 method+path 生成稳定名）；保留 `description`/`example` 等用于文档。
- 代码生成：
  - 模型：对象→`struct`；枚举→`enum` + `FromJson`/`ToJson`；`oneOf` 先拒绝或降级为 `Json`（必须显式警告）。
  - 描述符：每个 operation 生成 `Endpoint::new(params=..., request_body=..., responses=...)`；参数用 `Param::new`；响应用 `ResponseSpec::new`。
  - handler：签名接收 `@moonapi.Context`，返回 `@moonasgi.Response`；未实现返回 `@moonapi.text(501, "TODO")`。
  - `main`：`@mooncat.serve(app.to_asgi(), port=...)`。
- 版本：在生成的 `moon.mod` 中固定经过测试的版本（例如 moonapi 0.17.4、mooncat 0.18.6、async 0.22.5、x 0.5.7）；README 给出升级指引。
- 测试：生成器自身的单元/golden 测试 + 生成工程的编译/运行测试；CI 使用 Windows/Linux 双平台（native）+ `moon check --target wasm`。
- 回环：moonapi 的 `app.openapi_json()` 输出作为“生成结果的自描述”，与原规格做规范化 diff；这是最强的一致性证据。

#### 6.1.8 最小可用版本与工作量

**MVP 定义（第 4 周末必须可演示）**

1. 输入 Petstore 3.0/3.1，生成一个可编译的 MoonBit 服务端。
2. 至少 3 个端点（GET path、GET query、POST JSON body），包含类型模型、校验、422 错误。
3. `moon run` 启动后，curl 可访问；`/openapi.json` 与原规格的关键字段一致。
4. 生成器有 CLI、README、CI、至少 10 个有意义 commit。
5. 发布到 mooncakes（生成器本身；生成工程不发布）。

**四周计划**

| 周 | 目标 | 交付 | 退出标准 |
|---|---|---|---|
| 第 1 周 | 接入/扩展 oas2moon_frontend + server IR + 模型生成 | `oas2server check`、Petstore 模型 golden test | 模型编译通过；诊断可读 |
| 第 2 周 | 路由/描述符/handler 生成 | 生成 Petstore 服务端，`app.handle` 测试通过 | 3 个端点跑通；422 正确 |

| 第 4 周 | 文档/示例/发布/演示 | README、demo、mooncakes、提案 | 可复现；10+ commits |

**预估工时**：120–180 小时（含测试/文档/CI），核心代码估计约 6–9k 行 MoonBit（含测试；这是估算，不是承诺）。以你的经验和 AI 辅助，属于“紧但可行”；最大不确定性是 OpenAPI 边界与 moonapi 版本适配，不是核心算法。

#### 6.1.13 替代方案：为什么不直接把 OpenAPI import 做进 mctl？

这是一个必须正面回答的问题，因为 mctl 已经解决了“spec → moonapi 脚手架”的大部分工程。

**mctl 路线（贡献/维护赛道）**

- 给 mctl 提一个 OpenAPI importer：把 OpenAPI 转成 `.api` spec 或直接生成 moonapi 代码。
- 优点：复用 mctl 的 codegen/模板/文档；与作者协作；符合赛事“社区维护项目”赛道；不需要新建一个项目。
- 缺点：mctl 是 moonbitstack 的项目，路线由作者决定；`.api` DSL 的表达力可能限制 OpenAPI 特性；贡献者需要遵循其风格/节奏；赛事要求“新项目”时不适合。

**独立 oas2server 路线（本报告首选）**

- 优点：可以完整针对 OpenAPI/JSON Schema 设计服务端 IR；可以快速迭代；可以差异化（回环、诊断、MCP）；新仓库/新项目符合你的目标。
- 缺点：需要自己维护 codegen/测试/文档；可能与 mctl 功能重叠；需要主动与 mctl 社区沟通，避免重复。

**建议**：

- 如果你更看重**低风险、生态协作、长期维护**，把 OpenAPI import 贡献给 mctl 是更优路径；这甚至可以作为“社区维护项目”参赛。
- 如果你更看重**独立项目、完整 OpenAPI 支持、快速做出差异化**，选 oas2server；同时在 README/issue 中说明与 mctl 的关系，必要时输出 `.api` 作为互操作格式。
- 两条路都不丢人；关键是不要同时做一半，导致两个都不完整。

**另一条路：在 oas2moon 仓库内扩展服务端生成**

- 优点：最大程度复用 OpenAPI 前端/诊断/命名；同一套测试/corpus；品牌连续。
- 缺点：客户端 IR 与服务端 IR 差异大（responses/security/descriptors），容易把仓库做成两套半成品；赛事要求“新项目”时，评审可能认为新增工作不够独立。
- 如果选这条，建议至少拆成独立包（如 `oas2moon_server`）+ 独立 README/验收证据，并在申报书中明确新增工作；否则优先新建仓库。

**推荐做法（考虑到 oas2moon 是你的前作）**

- **新仓库 `oas2server`，依赖 `oas2moon_frontend`（MIT）做 OpenAPI 解析/诊断**；新代码集中在 server IR、moonapi codegen、回环/编译测试。
- 这样既保留“新项目”的独立性，又复用你的前端资产；申报书披露“前作 + 新增服务端工作”，不把前作算成本届成果。
- 如果评审认为重叠，退一步：把服务端生成做成 `oas2moon_server` 子包，走维护赛道；或把 OpenAPI import 贡献给 mctl。

### 6.2 候选 2（高上限备选）：moonquery — 纯 MoonBit 的 SQLite SQL 查询引擎

#### 6.2.1 一句话定位

**在 MoonBit 里直接对 SQLite `.db` 文件执行只读 SQL，编译到 native/WASM/JS，无 FFI、无 sql.js、无 Node/Python 运行时；为浏览器本地数据、边缘分析和 Agent 数据工具提供“纯 MoonBit 的查询层”。**

#### 6.2.2 三个完整使用场景

**场景 A：浏览器/WASM 本地数据分析**

- 用户在网页里上传一个 `.sqlite` 文件（例如从桌面应用导出的数据），想筛选、聚合、排序，生成图表。
- 今天：引入 sql.js（SQLite WASM + JS 胶水），体积/初始化/内存成本高；或者上传到服务器。
- 用 moonquery：MoonBit/WASM 直接读文件字节，执行 `SELECT ... WHERE ... GROUP BY ...`，结果以 JSON/表格返回；数据不离开浏览器。
- 价值：**本地、隐私、无 JS 运行时、可嵌入 MoonBit 前端**。

**场景 B：边缘/Serverless 的 SQLite 快照分析**

- 边缘函数拿到一个 SQLite 快照（例如离线同步的数据库），需要做只读分析/报表。
- 今天：依赖 native SQLite 绑定（平台相关），或者调用外部服务。
- 用 moonquery：纯 MoonBit 编译到目标平台，无 C 依赖；对只读快照安全。
- 价值：**可移植、确定性、无 FFI 供应链风险**。

**场景 C：Agent 的本地数据工具**

- Agent 需要读取用户提供的 SQLite 文件并回答“上个月销售额是多少”。
- 今天：Agent 调用 Python/SQLite 工具，或把数据上传到服务。
- 用 moonquery：Agent 运行时（MoonBit/WASM）内嵌查询引擎，SQL 只读、可限制扫描行数/超时，结果结构化返回。
- 价值：**在 Agent 沙箱内完成数据查询，不需要外部进程**。

#### 6.2.3 现有解决方案与竞品

| 方案 | 能力 | 局限 | 与 moonquery 的关系 |
|---|---|---|---|
| **chen333w/moon-lite** 0.3.0 | 纯 MoonBit 读 SQLite 文件：页、b-tree、record、overflow；全表扫描；native/WASM | **无 SQL 引擎、无写入、拒绝 WAL** | **基础**；moonquery 复用其文件/b-tree/record 层 |
| **prowk/moonsqlitefile** 0.8.1 | 纯 MoonBit 只读文件解析/检查 | 同样无 SQL | 竞品/参考 |
| **geniuszby/pagelens** 0.1.0 | 只读 SQLite/WAL 分析器 | 分析工具，非查询引擎 | 竞品/参考 |
| **uiwcvb/moonsql** 0.1.0 | 纯 MoonBit 嵌入式关系 SQL 引擎（B+tree、WASM） | **包下载 404、`moon add` 因旧 `moon.mod.json` 失败；当前工具链不可安装**；不是 SQLite 文件兼容 | 概念上最接近；但当前不可用，不能算有效竞品；若作者修复，需重新评估 |
| **moonbit-community/sqlite3 / moonbitstack/moonsqlite / KKKIIO/sqlite** | native/JS 绑定，完整 SQLite | 依赖 C/Node，平台相关 | 不同赛道；moonquery 的“纯实现”是差异 |
| **sql.js / SQLite WASM** | 完整 SQLite，成熟 | 体积/JS 胶水/内存；非 MoonBit 原生 | 最强外部竞品；moonquery 必须用“纯 MoonBit/小/可嵌入”差异化 |
| **moonlake** | SQL over CSV/Parquet，native+WASM | 不是 SQLite 文件 | 互补；可共享 SQL 执行经验 |
| **moonbit-community/sqlparser** 0.5.2 | 多方言 SQL lexer/parser/AST | 只有 parser，无执行器 | **可复用**；moonquery 实现 binder/planner/executor |

`[已验证-一手，README/API]`

**关键判断**：

- 纯 MoonBit 的 SQLite **读取器**已有至少 3 个，说明“在 MoonBit/WASM 里读 SQLite”有真实兴趣。
- 纯 SQL 引擎有过尝试（`uiwcvb/moonsql`，2026-08），但当前包不可安装、也不是 SQLite 文件兼容；**“可用于 SQLite 文件的纯 MoonBit SQL 执行器”仍然是缺口**。`[已验证-本地安装失败 + 描述级]`
- `moon-lite` 明确写“no query engine: there is no SQL, only full-table scans”。
- 外部 sql.js 很强；moonquery 不能宣称“替代 SQLite”，只能定位为“MoonBit 原生、只读、可嵌入的查询层”，并用体积/无 FFI/全后端/确定性作为差异。

#### 6.2.4 差异化与“为什么是 MoonBit”

1. **纯实现、无 FFI**：不依赖 C SQLite、Node、Python；可编译到 native/WASM/JS；适合边缘/浏览器/Agent 沙箱。
2. **全后端一致**：同一套查询代码在服务端和浏览器跑；MoonBit 的多后端是结构性优势。
3. **小体积/可嵌入**：不携带整个 SQLite 引擎；只读分析场景可以裁剪。
4. **安全只读**：不写文件、不执行 DDL/DML，天然适合不可信输入；可加扫描行数/超时/内存限制。
5. **与 MoonBit 数据栈协同**：结果直接是 MoonBit 类型/JSON，接 MoonFrame/图表/Agent 工具。

#### 6.2.5 核心功能（MVP）

**输入**

- SQLite 3 文件（rollback journal 模式；非 WAL；UTF-8/UTF-16；含 overflow；支持 `WITHOUT ROWID` 读取）。
- 通过 bytes 传入（文件系统、HTTP、浏览器上传均可）。

**SQL 子集**

- `SELECT`：列投影、别名、`*`、表达式。
- `WHERE`：比较、`AND/OR/NOT`、`IS NULL`、`IN`、`BETWEEN`、`LIKE`（简单模式）。
- `ORDER BY`、`LIMIT`/`OFFSET`。
- `GROUP BY` + 聚合：`COUNT/SUM/AVG/MIN/MAX`。
- `DISTINCT`。
- `INNER JOIN` / `LEFT JOIN`（嵌套循环）。
- 基础函数：字符串（length/lower/upper/substr/trim）、数学（abs/round）、`COALESCE`、`NULLIF`。
- 类型：NULL/INTEGER/REAL/TEXT/BLOB；SQLite 的动态类型与亲和性（按子集实现）。

**输出**

- 类型化结果集（列名/类型/行）；JSON/CSV 输出；CLI 表格。
- `EXPLAIN`（简化）：显示扫描/过滤/聚合/连接计划。
- 查询限制：最大行数、最大扫描页数、超时（宿主可配）。

**明确不做（MVP）**

- 写入/DDL/DML/事务/触发器/视图。
- WAL 恢复（检测到 WAL 直接报错，提示先 checkpoint）。
- 索引遍历（全表扫描；索引优化 v2）。
- 窗口函数、CTE、子查询（v2）、`RIGHT/FULL JOIN`、复杂 collation、加密、attached DB。
- 完整 SQLite 语义（日期函数、JSON1、FTS、扩展）。

#### 6.2.6 技术路径

```text
SQLite bytes
   │
   ▼
[moon-lite] 文件头/页/b-tree/record/overflow  → 行（Value）
   │
   ▼
[sqlparser] SQL text → AST
   │
   ▼
[binder]  表/列解析、类型/亲和性、别名、作用域
   │
   ▼
[planner]  scan/filter/project/aggregate/join/sort/limit
   │
   ▼
[executor]  Volcano/迭代器；NULL 三值逻辑；聚合/连接
   │
   ▼
结果集（JSON/CSV/CLI/库 API）
```

**实现要点**

- 复用 `moon-lite`（Apache-2.0）的 b-tree/record 层；如果其 API 不够，fork 并保持上游同步。
- 复用 `moonbit-community/sqlparser`（Apache-2.0）的 AST；只实现子集，遇到不支持语法给明确错误。
- 自己实现 binder/planner/executor；这是项目的核心新工作。
- 测试：与 Python `sqlite3` 做差分测试（同一 DB、同一查询，比较结果）；corpus 包括 Chinook、生成的多类型表、中文/UTF-16、overflow、NULL、边界值。
- 性能：对 ≤100MB DB 做基准；明确“全表扫描”的定位，不做虚假性能承诺。
- WASM demo：浏览器读取上传文件 → 查询 → 表格/JSON；可复用 MoonBit 前端框架（rabbita/sumi）或最小 HTML。

#### 6.2.7 最小可用版本与工作量

**MVP 定义**

1. 读取真实 SQLite 文件（含中文、REAL、NULL、overflow）。
2. 支持单表 `SELECT` + `WHERE` + `ORDER BY` + `LIMIT` + 聚合 + `GROUP BY`。
3. 支持两个表的 `INNER JOIN`。
4. CLI + 库 API；差分测试通过率 ≥99%（支持子集内）。

| 评审认为“重复 SQLite” | 中 | 中 | 强调纯实现/全后端/只读安全；不宣称替代 SQLite |

#### 6.2.10 尚未验证的关键假设与验证方法

| 假设 | 当前证据 | 验证方法 | 不成立时 |
|---|---|---|---|
| B1：MoonBit/WASM 用户需要查询 SQLite，而不是用 sql.js/JS FFI | 3 个纯只读解析器；WASM 本地数据场景 | 访谈 5–10 个 MoonBit 前端/数据/Agent 开发者；做 sql.js vs moonquery 的体积/集成对比 | 放弃或转向“SQLite 写入器” |
| B2：只读分析是足够大的首个场景 | moon-lite 明确只读；分析/报表需求 | 收集 10 个真实 DB 用例；统计 WAL 比例 | 增加 WAL 读取或写入（大幅加风险） |
| B3：SQL 子集能在一个月内达到可接受正确性 | sqlparser 已有 AST；moon-lite 已读行 | 第 1 周差分测试；目标 ≥99% | 缩到单表 + 聚合 |
| B4：性能对目标 DB 可接受 | 全表扫描；MoonBit native 性能尚可 | 基准 ≤100MB；对比 sql.js | 限制 DB 大小/加索引 |
| B5：WASM demo 可行 | moon-lite 声称全后端；本地 native 读通 | 编译 wasm-gc/wasm，浏览器加载 | 只做 native/CLI，WASM 延后 |

#### 6.2.11 证据等级

- `[已验证-一手]`：moon-lite 只读/无 SQL/拒绝 WAL；sqlparser 有 AST；本地 native 读 SQLite 成功；`uiwcvb/moonsql` 的 zip 404、`moon add` 因旧 `moon.mod.json` 失败（当前不可安装）。
- `[已验证-描述级]`：其他只读解析器/绑定存在；无纯 SQL 引擎。
- `[推断]`：MoonBit/WASM 用户对 SQLite 查询的需求；sql.js 替代意愿。
- `[未知]`：WAL 在目标用户 DB 中的比例；一个月能否达到可接受正确性。

### 6.3 候选 3（条件备选，不推荐作为首选）：mooncert — MoonBit 包兼容性与质量门禁

#### 6.3.1 一句话定位

**一条命令/一个 GitHub Action，对 MoonBit 包做跨 target、跨工具链版本的构建/测试、API 兼容、文档示例、覆盖率和许可证检查，输出可复现报告与徽章；把“这个包现在还能不能用”变成 CI 可判定的事实。**

#### 6.3.2 三个使用场景

1. **包作者**：在 CI 中加 `mooncert`，每次 PR 检查 native/JS/WASM 构建、测试、API 兼容、README 示例；工具链升级时提前发现破坏。
2. **包使用者**：安装前运行 `mooncert inspect <pkg>`，查看支持的 target/工具链、测试/覆盖率、文档示例、许可证、最近发布；降低“装了就坏”的风险。
3. **生态维护者**：对一批包跑兼容矩阵，生成“MoonBit 新版本破坏面”报告；为工具链升级提供数据。

#### 6.3.3 现有工具与缺口

| 工具 | 能力 | 缺口 |
|---|---|---|
| `mooncompat` / `moonguard` | 公共 API 兼容/SemVer 检查 | 只做 API diff |
| `mooncov` / `moon_cove` | 覆盖率 | 只做覆盖率 |
| `harborcheck` | README 示例验证 | 只做示例 |
| `mooncram` | CLI/脚本测试 | 只做 CLI 测试 |
| `turtles` / `moon_mutest` | 变异测试 | 只做变异 |
| `mare_mark` | 基准/统计对比 | 只做基准 |
| `pubman` / `moon-bump` / `moon-release` | 打包/发版 | 只做发布 |
| 官方 `moon check/test` | 构建/测试 | 不做跨版本矩阵/质量门禁 |

`[已验证-描述级]`

**缺口**：工具很多，但没有一个“一条命令跑完整质量门禁 + 跨 target/版本 + 统一报告/徽章”的集成层。这不是技术空白，而是 **集成/UX 空白**。

#### 6.3.4 为什么它是条件备选

**支持理由**

- 生态的真实矛盾是“数量增长快、质量/兼容性不足”；3,498 模块、单月 1,291 新增、工具链高频变更。
- 包作者和消费者都需要一个可信的质量信号；官方也在强调“可用、稳定、可持续维护”。
- 技术风险低，一个月可交付；可与现有工具集成，而不是重写。

**反对理由（更重要）**

- 章程明确把“mooncakes.io 的发布审计工具”列为“不建议”的官方软件方向；质量门禁与之相邻，容易被评审视为官方领地。
- 技术纵深较浅：核心是编排现有工具 + 解析输出 + CI；评审可能认为“工程量大但技术含量一般”。
- 采用依赖官方/社区背书；如果官方不做推荐，包作者没有动力加门禁。
- 维护成本高：要跟踪多个工具、多个 target、多个工具链版本；一个人长期维护压力大。
- 演示效果弱：一个 CI 报告/徽章，不如一个可运行的服务端/查询引擎直观。

**结论**：如果你更看重“低风险完成一个有用的生态工具”，它可以做；但如果你要冲季度奖/首选项目，候选 1/2 更好。**不要为了凑第三个而选它。**

#### 6.3.5 如果要做，MVP 边界

- 配置：`mooncert.toml`（targets、toolchains、checks、阈值）。
- 检查：`moon check`/`moon test`（native/js/wasm-gc）、API diff、README 示例、覆盖率阈值、许可证/OSI、mooncakes 元数据。
- 输出：终端摘要、JSON、JUnit/SARIF、徽章 JSON。
- 集成：GitHub Action（安装工具链、缓存、矩阵）。
- 不做：托管服务、自动修 PR、恶意代码扫描、替代官方 registry 审核。
- 预估：100–150 小时；风险低，但需要 5–10 个包作者试用才有意义。

#### 6.3.6 未验证假设

| 假设 | 验证方法 | 不成立时 |
|---|---|---|
| 包作者愿意加质量门禁 | 访谈 5–10 个活跃包作者；看他们现有 CI | 放弃 |
| 官方不会很快自己做 | 与官方/社区沟通；观察 mooncakes roadmap | 放弃或转为官方贡献 |
| 跨工具链安装/运行可自动化 | 在 Windows/Linux 试装 2–3 个版本 | 缩到当前版本 + target 矩阵 |
| 维护成本可接受 | 估算工具/版本数量；设计插件化 | 缩小检查范围 |

### 7.2 Spike 1：moonapi 服务端在 Windows 原生跑通

**目标**：验证 oas2server 的生成目标——类型化路由、路径参数校验、JSON body 校验、OpenAPI 回吐——在本机可运行。

**最小代码形态**（与实际生成器目标一致）：

```moonbit
struct Pet {
  id : Int32
  name : String
  tag : String?
} derive(ToJson, FromJson)

fn Pet::schema() -> @moonapi.Schema {
  @moonapi.Schema::object("Pet", [
    @moonapi.Field::new("id", SInt),
    @moonapi.Field::new("name", SStr),
    @moonapi.Field::new("tag", SStr, required=false),
  ])
}

async fn main {
  let app = @moonapi.App::new()
  let get_pet = @moonapi.Endpoint::new(
    params=[@moonapi.Param::new("petId", InPath, schema=SInt)],
    responses=[
      @moonapi.ResponseSpec::new(200, body=Pet::schema()),
      @moonapi.ResponseSpec::new(404, description="Not Found"),
    ],
  )
  app.get("/pets/{petId}", ctx => {
    let errs = get_pet.validate(ctx)
    if errs.length() > 0 {
      @moonapi.unprocessable(errs)
    } else {
      let id = @string.parse_int(ctx.param("petId").unwrap()) catch { _ => 0 }
      @moonapi.json(200, Json({ id, name: "Rex", tag: Some("dog") }))
    }
  }, endpoint=get_pet, summary="fetch a pet")
  // POST /pets 类似，略
  @mooncat.serve(app.to_asgi(), port=12001) catch { err => println("stopped: \{err}") }
}
```

**实测结果**

| 请求 | 结果 |
|---|---|
| `GET /pets/1` | `200`，`{"id":1,"name":"Rex","tag":"dog"}` |
| `GET /pets/abc` | `422`，`{"detail":[{"type":"int_parsing","loc":["path","petId"],"msg":"Input should be a valid integer..."}]}` |
| `POST /pets`（合法 JSON） | `201`，`{"id":2,"name":"Milo"}` |
| `POST /pets`（非法 JSON） | `422`，同时报告 `int_type` 与 `missing name` 两条错误 |
| `GET /openapi.json` | `200`，`openapi: 3.1.0`，包含 `/pets/{petId}`、`/pets`、`components.schemas.Pet`、`required: ["id","name"]` |

`[已验证-本地]`

**结论**：

- oas2server 不需要自己实现路由/校验/文档；这些由 moonapi 提供，生成器只需生成正确的模型、描述符和 handler。
- 生成代码的形态是可行的、可读的、可编译的；本地从 `moon check` 到 `moon run` 约 20–30 秒（增量）。
- OpenAPI 回吐可作为回环测试的基准；moonapi 输出的是 3.1，且保留 `$ref`/`required`/path 参数。

### 7.3 Spike 2：纯 MoonBit 读取 SQLite（备选方向）

**目标**：验证 moonquery 的底层读取路径在 Windows 原生可用，包括中文、REAL、多行。

**步骤**

1. 用 Python `sqlite3` 生成 `test.db`：`users(id INTEGER PRIMARY KEY, name TEXT, score REAL)`，插入 Alice/Bob/张三。
2. MoonBit 使用 `chen333w/moon-lite/db` + `moonbitlang/x/fs` 读取并打印。

**实测输出**

```text
table users
  1: [1, Alice, 9.5]
  2: [2, Bob, 8]
  3: [3, 张三, 7.25]
```

`[已验证-本地]`

**结论**：

- 纯 MoonBit 的 SQLite 文件/ b-tree / record 读取在 Windows 原生可用；中文与 REAL 正常。
- moon-lite 的 API 是“表 + 行 + 值”，没有 SQL；要成为 moonquery，需要自己实现 binder/planner/executor。
- 这是“可做”的证据，不是“一个月能做完”的证据；SQL 语义与 WAL 仍是主要风险。

### 7.4 版本坑与兼容性

**实测**：`moon add` 默认拉到 `moonbitlang/async@0.22.7`，在 `moon 0.1.20261016` 上编译失败：

```text
Cannot find import 'moonbitlang/core/async' in moonbitlang/async@0.22.7
```

固定到 `0.22.5` 后通过。

`[已验证-本地]`

**含义**：

- MoonBit 的工具链/包版本耦合仍然明显；生成器/项目必须固定经过测试的版本，并提供升级指南。
- 如果在 11 月赛季开始前升级工具链，需要重新跑一遍兼容矩阵；不要假设“最新版本一定兼容”。
- 这也是候选 3（质量门禁）的真实痛点之一。

### 7.5 构建体积与 Windows 细节

- 依赖源码 `.mooncakes` 约 **29 MB**，构建目录 `_build` 约 **76 MB**（debug/native，含 moonapi/mooncat/async/x 等）。
- `moon new` 在 Windows 无开发者模式时会报“failed to create file symlink: README.md -> README.mbt.md”；不影响构建，手动复制 README 即可。
- 原生链接需要 MSVC Build Tools；没有 C 编译器的用户会卡在 native。README 必须写明；CI 覆盖 Linux 作为替代。

### 7.6 技术可行性结论

| 项目 | 核心路径 | 可行性 | 主要不确定性 |
|---|---|---|---|
| oas2server | OpenAPI 解析 → moonapi 描述符/模型 → 生成工程 → 编译/运行/回环 | **高**（运行时已验证；生成器是文本生成 + 测试） | OpenAPI 子集边界、moonapi 版本、需求 |
| moonquery | moon-lite 读取 → sqlparser AST → binder/planner/executor | **中**（读取已验证；执行器是核心工作量） | SQL 语义、WAL、性能、一个月工期 |

## 8. 综合对比与最终建议

### 8.1 评分表（主观，用于排序，不是事实）

评分 1–5，权重按“赛事 + 长期价值”设定。`[主观判断]`

| 维度 | 权重 | oas2server | moonquery | mooncert |
|---|---:|---:|---:|---:|
| 需求真实性（外部 + MoonBit） | 25% | 4 | 4 | 3 |
| 生态缺口/现有方案不足 | 20% | 4 | 5 | 3 |
| MoonBit 结构性优势 | 15% | 4 | 5 | 3 |
| 一个月可交付性 | 15% | 4 | 2 | 5 |
| 采用/分发路径 | 15% | 4 | 3 | 3 |
| 长期维护价值 | 10% | 5 | 5 | 4 |
| **加权** | 100% | **4.10** | **4.00** | **3.40** |

**解释**：

- oas2server 的“需求真实性”不是满分：MoonBit 后端团队是否普遍有 OpenAPI 仍未验证；但外部工作流成熟、MoonBit 侧缺口明确、可交付性高。
- moonquery 的“缺口/优势”接近满分：纯 MoonBit、全后端、无 FFI 是结构性差异；但“一个月可交付性”只有 2，风险高。
- mooncert 的“可交付性”满分，但“缺口/优势/需求”较弱，且官方领地风险。

### 8.2 决策树

```text
你能在 7 天内找到 5 个以上 MoonBit 后端/API 团队，
并且他们明确说“我们有 OpenAPI，想要 MoonBit 服务端”吗？
├── 是 → 选 oas2server（首选）
│         └── 同时问：他们要不要 MCP 工具？要 → v1.1 加 --mcp
└── 否
    ├── 你能找到 5 个以上 MoonBit/WASM 数据/Agent 开发者，
    │   并且他们明确说“我们需要在 MoonBit 里查 SQLite”吗？
    │   ├── 是 → 选 moonquery（但先接受只读/WAL 限制）
    │   └── 否 → 不要强行做新库
    │            → 考虑：给 mctl 提 OpenAPI import（维护赛道）
    │            → 或做一个小而完整的工具（候选 3 的缩小版）
    └── 你能接受“官方可能自己做”的风险，
        并且有 5 个以上包作者愿意试用吗？
        ├── 是 → 选 mooncert（条件备选）
        └── 否 → 停止，不要凑第三个
```

### 8.3 为什么首选是 oas2server

1. **风险调整后最优**：需求外部验证充分、MoonBit 缺口明确、运行时已成熟、生成器是可控的文本生成 + 测试，不是深水区算法。
2. **与你已有能力形成复利**：你有 oas2moon 的 OpenAPI 前端/IR/诊断/代码生成经验；oas2server 是同一能力的服务端延伸，不是从零学新领域。
3. **有清晰的采用路径**：接 moonapi/mctl 生态；生成工程可直接运行；可输出 `.api` 与 mctl 互通；可扩展 MCP。
4. **有清晰的差异化**：标准输入（OpenAPI）、MoonBit 原生、描述符/校验/回环、全后端、一份规格三产物（server/client/MCP）。
5. **有清晰的验收证据**：生成工程可编译/可运行/可测试；`/openapi.json` 回环是机器可验证的一致性证据；CI 绿、mooncakes 发布、demo 可复现。
6. **失败可退**：如果 OpenAPI 需求验证失败，生成器的 frontend/IR/codegen 经验可以迁移到 mctl/其他 spec，或转向候选 2；不会全盘归零。

### 8.4 什么情况下应该改选 moonquery

- 你访谈后发现：MoonBit 后端团队几乎没有 OpenAPI，或者他们更愿意用 moonapi 代码优先；
- 但 MoonBit/WASM 数据/Agent 开发者明确需要“在 MoonBit 内查 SQLite”，并且能接受只读/WAL 限制；
- 你愿意接受更高的技术风险，追求“纯 MoonBit 数据基础设施”的长期价值；
- 你能在一个月内把范围压到“单表 SELECT + 聚合 + 可选 JOIN”，并有差分测试兜底。

### 8.5 什么情况下应该改选 mooncert / 或不做第三个

- 你更看重“低风险完成一个有用的生态工具”，而不是冲季度奖；
- 你能拿到 5+ 包作者的试用承诺；
- 你确认官方不会在近期做同样的门禁；
- 否则，不要为了“凑三个”而做；把精力放在首选项目的质量和演示上。

### 8.6 什么情况下应该“不做新项目”

- 7 天内无法找到 5 个真实用户/明确痛点；
- 你发现自己只是“想写一个库”，而不是“解决一个被验证的问题”；
- 首选项目的两个关键假设（A1 需求、A2 moonapi 目标）都不成立；
- 这时更理性的选择是：**参与 mctl/moonapi 的 OpenAPI import**（维护赛道/社区贡献），或者做一个更小的工具，而不是硬推一个完整项目。

### 9.2 第 1 周：接入 oas2moon_frontend + server IR + 模型生成

- 接入/扩展 `oas2moon_frontend` 解析 OpenAPI 3.0/3.1 JSON（YAML 可后置）；建立 `Spec`/`Operation`/`Schema` 的服务器 IR。
- 实现支持度检查：遇到 `oneOf/anyOf/allOf/discriminator/callbacks/links/webhooks` 等，输出 JSON Pointer + 明确原因。
- 生成 `models.mbt`：对象/枚举/数组/基础类型/可选字段；`derive(ToJson, FromJson)`；`T::schema()`。
- Golden test：Petstore 的 `Pet`/`Error` 等模型生成结果固定。
- 里程碑：`oas2server check petstore.yaml` 可运行；模型生成物可编译。

### 9.3 第 2 周：路由/描述符/handler/服务端

- 生成 `app.mbt`：`Endpoint::new(params=..., request_body=..., responses=...)`；路径参数/查询参数/JSON body。
- 生成 `handlers.mbt`：每个 operation 一个类型化 handler，默认 501。
- 生成 `main.mbt`：`mooncat.serve(app.to_asgi(), port=...)`。
- 运行时测试：不启 socket，直接 `app.handle` 发请求，断言 200/201/422。
- 里程碑：Petstore 生成工程 `moon run` 可启动；3 个端点 curl 通过；第一个 demo 视频。

### 9.4 第 3 周：约束/安全/回环/corpus

- 约束：`min/max`、`minLength/maxLength`、`pattern`、`enum`、`nullable`、`required`。
- 安全：`securitySchemes` 声明（bearer/apiKey/basic/oauth2 声明），生成 moonapi 元数据；不实现 OAuth 流程。
- 回环：生成工程 `/openapi.json` 与原规格规范化 diff；记录允许的差异（排序/描述/默认值）。
- Corpus：Petstore + GitHub 子集 + Stripe 子集 + 至少 1 个真实内部规格；每个至少 golden/compile 测试。
- 里程碑：回环报告可读；CI 在 Windows/Linux native + wasm check 绿。

### 9.5 第 4 周：文档/示例/发布/演示/缓冲

- README：安装、Quickstart、支持矩阵、限制、版本兼容、故障排查。
- Demo：`demo/petstore`（生成工程 + curl 脚本 + 截图/短视频）。
- 发布：mooncakes `moon publish`；CHANGELOG；LICENSE/NOTICE；Issue/PR 记录。
- 提案：1 页，人工写；附仓库/演示链接。
- 缓冲：留给 OpenAPI 边界 bug、moonapi 版本问题、评审反馈。
- 里程碑：验收清单全部打勾；10+ 有意义 commits；可复现。

### 9.6 Kill criteria（止损线）

- 第 1 周末：如果 `check` + 模型生成还不能编译，砍掉复杂 schema，只做 object/array/enum/primitive。
- 第 2 周末：如果生成工程不能运行 3 个端点，砍掉 query/header，只保留 path + JSON body。
- 第 3 周末：如果回环差异无法解释/收敛，改为“生成工程 + 人工核对清单”，不宣称自动回环。
- 第 0 周需求验证：如果 5 个访谈中 <3 人明确需要，停止或转向候选 2；不要因为“已经写了几天”而继续。

## 11. 对抗性审查总结：最强的反方观点与回应

### 11.1 “OpenAPI→服务端在外部已经解决了，为什么还要 MoonBit 版？”

**反方**：openapi-generator（26.8k stars）、oapi-codegen（8.6k）已经成熟；MoonBit 用户可以用它们生成 Node/Go/TS 服务端，或者用 mctl 的 `.api`。一个 MoonBit 生成器只是“再实现一遍”。

**回应**：

- 生成到**另一种语言**不能解决“团队要用 MoonBit 写服务端”的问题；跨语言重写/移植成本高。
- mctl 要求把 OpenAPI 重写成 `.api`，对已有契约是额外维护；而且 `.api` 的表达力弱于完整 OpenAPI/JSON Schema。
- oas2server 的差异不是“模板”，而是 **moonapi 描述符 + 校验 + OpenAPI 回吐 + 全后端**；生成物能直接跑，回环可机器验证。
- 如果目标用户根本不想用 MoonBit 写服务端，这个项目就不成立；这正是 A1 必须验证的原因。

**结论**：这是首选项目最大的风险；如果 7 天内无法找到 5 个真实用户，应转向候选 2。

### 11.2 “moonquery 只是玩具，sql.js 已经是完整 SQLite”

**反方**：sql.js/SQLite WASM 功能完整、成熟；moonquery 只读、无 WAL、无写入，性能还可能是全表扫描。

**回应**：

- moonquery 不宣称替代 SQLite；它解决的是“MoonBit/WASM/Agent 内嵌、无 JS/FFI、只读安全”的细分场景。
- 纯 MoonBit、全后端、小体积、确定性是结构性差异；对 MoonBit 生态是“有没有”的问题，不是“好不好”的问题。
- 但只读/WAL 限制让它的适用面变窄；必须用真实用户验证，而不是假设“WASM 用户都需要”。

**结论**：高上限、高风险；只有在 B1/B2 验证通过时才值得投入。

### 11.3 “mooncert 是官方该做的事”

**反方**：章程明确不建议做 mooncakes 发布审计类官方工具；质量门禁靠近官方领地，且技术浅。

**回应**：

- 同意。它是条件备选，不是首选；只有在官方不反对、包作者愿意试用时才做。
- 如果要做，应定位为“第三方 CI 集成层”，而不是“registry 审核”；并且要复用现有工具，不重写分析器。

**结论**：不建议为了凑第三个而做。

### 11.4 “AI/Agent 是 2026 最大的趋势，为什么不做 Agent 项目？”

**反方**：MCP 91k stars、Agent 框架火热；MoonBit 官方也在推 Agent；做 Agent 项目更容易讲故事。

**回应**：

- 趋势不等于空白：MoonBit 已有 moonmcp、workflow、moonkoog、MoonRetrieve、openseek 等；外部有更多成熟方案。
- oas2server 的 `--mcp` 扩展让项目**自然接入 Agent**（一份 OpenAPI → REST + 客户端 + MCP 工具），而不是赌一个独立的 Agent 产品。
- 如果要做纯 Agent 项目，必须回答“为什么必须是 MoonBit”，否则很容易变成又一层胶水。

**结论**：AI 是加分项，不是立项理由；首选项目的 AI 切入点是“让真实 API 变成 Agent 工具”，而不是“再造 Agent 框架”。

### 11.5 “你已经有 oas2moon，oas2server 是不是自我重复？”

**反方**：同一作者、同一 OpenAPI 前端，换一个输出方向，是否算新项目？评审会不会认为在刷项目？

**回应**：

- oas2moon 是 **客户端 SDK 生成器**（OpenAPI → 调用方代码）；oas2server 是 **服务端生成器**（OpenAPI → 被调用方代码 + 校验 + 文档）。方向、IR、运行时、测试都不同。
- 新项目的核心新工作是 **Server IR + moonapi 描述符/路由/handler 生成 + 回环测试**；前端可复用/参考，但必须披露。
- 如果评审认为重叠，可以把 oas2moon 作为依赖/前作，强调新增工作；或者把 OpenAPI import 贡献给 mctl，走维护赛道。
- 既然 oas2moon 是你的前作，复用它的前端是**降低风险**，不是刷项目；关键是新增的服务端工作要独立、可验证、可演示。
- 这也是一个机会：**同一份 OpenAPI，客户端 + 服务端 + MCP**，是 oas2moon 单独做不到的生态价值。

**结论**：披露 + 差异化 + 新增工作足够，但必须在申报书中主动说明，不能藏着。

### 11.6 “一个月做不完”

**反方**：OpenAPI 太大，moonapi 还在变，Windows 原生还有坑；一个人一个月只能做玩具。

**回应**：

- 本地已验证运行时；生成器是文本生成 + golden/compile/runtime 测试，不是编译器级工程。
- 范围已压到“Petstore 级 CRUD + 常用子集”；不支持的特性显式拒绝，不追求完整 OpenAPI。
- 有止损线（9.6）；第 2 周不能跑 3 个端点就砍范围。
- 最大风险不是技术，而是需求；所以第 0 周先验证。

**结论**：可行，但必须严格执行“垂直切片 + 止损”。

## 12. 结论

### 12.1 最终建议

**推荐首选：oas2server（OpenAPI 3.x → MoonBit 类型化服务端脚手架）。**

它不是“最性感”的项目，但在 2026 年 10 月的 MoonBit 生态里，它同时满足：

- 外部需求被验证（OpenAPI→服务端是成熟工作流）；
- MoonBit 侧缺口明确（moonapi 代码优先、mctl 用自有 DSL、oas2moon 只做客户端）；
- 与你的能力复利（oas2moon 前作的 OpenAPI 前端/IR/代码生成可直接复用）；
- 一个月可交付（运行时已验证；生成器是可控的文本生成 + 测试）；
- 有机器可验证的质量证据（编译/运行/回环/CI）；
- 有生态协同与 AI 扩展（moonapi/mctl/oas2moon + `--mcp`）。

**备选：moonquery（纯 MoonBit 的 SQLite 只读查询引擎）。**  
只有当你验证了 MoonBit/WASM 数据/Agent 用户的真实需求，并接受只读/WAL 限制时，才建议选它；它的上限更高，但失败概率也更高。

**条件备选：mooncert（包兼容性/质量门禁）。**  
只有在你能拿到包作者试用承诺、且确认官方不反对时，才建议做；不要为了凑第三个而做。

## 附录 D：术语

| 术语 | 含义 |
|---|---|
| OpenAPI | REST API 的机器可读契约规范；3.0/3.1 为当前主流 |
| 契约优先（contract-first） | 先写 OpenAPI/IDL，再生成客户端/服务端/文档 |
| moonapi | MoonBit 的类型化 Web 框架；路由 + 校验 + OpenAPI 回吐 + ASGI |
| mctl | MoonBit 的 `.api` DSL 代码生成器（← goctl），生成 moonapi 脚手架 |
| oas2moon | 你的 OpenAPI → MoonBit 客户端 SDK 生成器（MIT） |
| ASGI | 异步服务器网关接口；moonapi 通过 moonasgi 与服务器解耦 |
| 描述符（descriptor） | moonapi 的 Endpoint/Param/Schema/ResponseSpec，驱动校验与 OpenAPI |
| 回环（round-trip） | 规格 → 生成代码 → `/openapi.json` → 与原规格对比 |
| WAL | SQLite 的 Write-Ahead Logging 模式；moon-lite 当前拒绝 WAL |
| 差分测试 | 同一输入分别跑两个实现，比较输出；用于 SQL/解析器正确性 |
| MVP | 最小可用版本；本项目定义为“可演示、可测试、可复现”的最小核心 |
