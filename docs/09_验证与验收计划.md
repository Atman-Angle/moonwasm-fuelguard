# MoonWasm FuelGuard 验证与生产验收计划

> **已归档（2026-11-20）：**验收口径被 [14 生产规格 v4 第 4 节](14_FuelGuard生产规格_v4.md) 取代；本文 §3 的需求变更评审通道保留为 14 第 3 节 fallback 的引用。本文仅作历史记录。

版本 v3，日期 2026-11-10。状态：计划；本文没有任何已通过结果。

## 1. 证据和支持范围

认证单位是工具 commit、费用模型、统一栈模型、profile/codegen、MoonBit/依赖/引擎版本、操作系统/CPU/原生栈配置和固定语料的组合。变更费用模型、helper 布局、支持指令或引擎版本均触发受影响验证。未运行的平台不得继承认证。

目标支持 Linux wasmoon 产品 runner 和 Wasmtime 独立测试驱动；Windows 只承担适用的 wasm 开发测试。两运行时测试同一份产物及配置，不用 Wasmtime 原生 Fuel 数值验证本项目计费。宿主 timeout/进程限额只用于测试失控保护，触发时判测试失败，不能算本工具成功拦截。

最低语料：60 个具名确定性用例，其中至少 20 个控制流/栈边界，以及来自至少 3 类工作负载的真实 MoonBit 构建产物。S01 已冻结四个认证输入（F0 基线 + 数据解析/解释器递归/计算密集三类负载）及其来源版本、构建命令、产物哈希与特性清单，见 [支持矩阵](implementation/support-matrix.md)；双引擎原模块执行仍待 S02，不等到最终测试才挑选兼容示例。数量不替代特性覆盖；未覆盖特性必须拒绝，`CONDITIONAL` 特性（memory.init/data.drop、externref table 增长、ref.null/is_null）必须补合成用例后才可声称支持。每个发布候选另跑至少 10,000 个固定种子生成/变异用例，记录种子和超时，失败最小化进入回归集。规模是工程门槛，不是形式化证明。

测试期使用独立的简单解释器/手算轨迹验证费用：不得复用生产计费分析器生成期望值。计费块采用预扣语义，不能拿逐指令终止点直接当作块预扣的预期结果。语义允许的差异在规格中逐项列出；禁止用“已解释”掩盖实现错误。

对非确定输入提供固定 host stub；NaN 结果采用语义分类比较，若要求按位一致则另设规范化 profile 并重新验证。宿主分配失败及原生栈先溢出不作为跨引擎确定性证据。start 阶段拿不到实例时保留诊断未知。

## 3. V5 性能实验

### 负载与比较组

覆盖算术直线代码、短/长循环、直接/间接调用、递归与大栈帧、bulk copy/fill、memory/table grow、至少三个真实 MoonBit 负载。基准必须校验输出，预算足够且不发生保护 trap；另测失败路径的诊断成本但不混入成功路径吞吐。

同一模型和语义下对照：原模块、Fuel-only、完整保护纯内联、完整保护共享helper、完整保护混合策略。wasmoon 和 Wasmtime 分别报告，不能把快引擎结果拿来抵消慢引擎。

### 测量方法

固定 CPU/OS/电源模式/编译选项/引擎配置；记录版本、commit、种子和输入哈希。每组至少5次预热、30个测量样本、3轮独立进程，交错或随机安排基线和候选顺序。业务生命周期样本每次新实例，从已编译模块开始实例化到显式入口业务完成，包含 core start section 内执行及实例化成本；引擎编译另计。适用负载另测热调用，初始化在热调用计时外，批量调用使用足够累计预算；不能复用耗尽实例。无有效热入口的 start-only 模块只测生命周期，不用空导出冒充热业务。短操作批处理到足以超出计时噪声，保存原始样本。

分别记录解析、分析、每次校验、编码、引擎编译、实例化、执行及端到端时间；报告中位数、p95、比值置信区间、wasm体积和插桩峰值内存。CPU/系统噪声导致区间过宽时重测并记录原因。构建期输入规模至少三档检查复杂度趋势，防止嵌套结构或数组复制退化。

### 初始硬性发布预算

以下是预先声明的工程预算，不是已实现性能，也不是通用行业标准：

- 对每个认证引擎，完整保护的固定生产负载集合业务生命周期时间比几何平均 <=2.0x；每个具名负载的中位数比 <=3.0x，p95 比 <=3.0x。适用的热调用负载集合分别执行同样门槛，集合和计时窗口提前冻结，不与生命周期或另一引擎混合平均。使用置信区间上界判断；边界不确定则补测。
- 对至少10 KiB的生产负载模块，体积比 <=2.0x；较小模块同时公布绝对增量，固定开销 <=10 KiB。压力/反例用例仍公布体积但不混入代表负载几何平均。
- 候选选择仅使用调优集：先满足正确性与各适用窗口预算，再最小化各引擎、各适用窗口中最差的几何平均开销；差异小于5%且落入噪声范围时优先更小、更简单的实现。冻结默认布局及选择记录后，最终独立验收集只确认该默认是否达标。保留全部候选原始结果，禁止只报胜者。
- 后续版本对冻结基线的执行/构建时间与峰值内存回退 >5%，经复测仍存在时阻塞发布并分析。
- 需要在首轮基准前为输入大小/嵌套等上限及最大支持输入的构建时间、峰值内存填写具体数值和参考硬件，未填写不得生产发布。

真实应用和压力微基准分开列出；严禁测试后挑选负载或降低门槛使结果过关。若预算确实不适合目标场景，作为独立需求变更先评审、保留旧结果并重新验收，不能写成已经满足原目标。原“超过3x只解释、不阻塞”规则失效。

## 4. 栈认证与鲁棒性

在各认证引擎配置上用深递归、最大允许local、复杂操作数栈、间接wrapper和冷失败路径探测安全范围。证明所支持输入和配置的测试中均先触发自身栈限制；抽样测试不构成任意机器保证。部署文档必须给保守上限和引擎设置，超出认证配置拒绝生产声明。

统一 C(f) 的推导、各候选 A(layout,f) <= C 的构建期审计、同时活跃帧的组合规则及原生栈映射依据必须随报告提供。参数/返回值数、local、嵌套及入口 wrapper 余量均有界。互斥/顺序辅助路径取峰值，嵌套链和仍存活 wrapper 相加；不得把 host 内部开销纳入未经承诺的保证。helper 不新增逻辑深度或现场失败点，受管边界的临界预算组合要在各布局得到相同诊断。

恶意格式和极深嵌套必须在有限时间/内存内明确拒绝；测试单独进程运行并设外部硬上限。runner import 禁止重入，超时、取消、初始化失败与资源trap分开分类。

## 5. 报告与状态

测试报告 schema 应包括：工具commit、工具/ABI/模型/profile版本、输入/输出哈希、运行时版本和配置、硬件、case ID、预期/实际状态、code/site、输出摘要、原始样本位置、复现命令、失败最小样例。

静态插桩 manifest 与测试报告分开；报告不可只引用可变分支名。site 指原始函数和指令路径，不承诺源码行号。每次报告明确“通过/失败/未执行”，不留空代表成功。

## 7. 执行阶段与报告判定

1. 环境冻结：完成 [验收报告模板](11_验收报告模板.md) 的版本、硬件、资源边界、成本表与语料哈希。任一必需字段未填，不能启动正式性能验收。
2. 快速门禁：静态check、单元测试、逐pass/独立校验及具名边界用例。失败先修复，不用性能测试掩盖功能失败。
3. 发布候选门禁：完整双引擎矩阵、10,000有效生成样本、输入故障和交付测试。
4. 性能门禁：在同一候选commit上执行A17-A20；优化导致产物改变时重过相关正确性检查。
5. 复核：报告中的每个PASS必须有实际证据；全部通过后才可称production-v1。

状态只允许PASS、FAIL、BLOCKED、NOT_RUN；不接受“基本通过”。必需项任何FAIL/BLOCKED/NOT_RUN均阻塞生产验收，禁止空白当成功。申报材料可以使用阶段结果，但需要明确尚未生产验收。

S17 统一入口为 `python3 -B integration/acceptance/check.py`。默认选择 A01–A24，
也可重复指定 `--group`。报告同时记录所选门禁的判定和全量判定。所选门禁全部通过退出
0，用例失败退出 1，环境或配置阻塞及所选门禁尚未实现退出 2。性能、包验证和最终独立
复核由后续分片提供。命令、产物路径及重放方式见 [验收入口](../integration/acceptance/README.md)。

## 8. 性能统计与差异补充规则

计时至少以进程为分组单位保留原始数据；时间比定义为候选与基线在同引擎同负载下的对应统计量之比。使用预先固定种子、至少10,000次分层bootstrap估计95%区间，先重采样进程组再重采样组内样本；算法、分位数插值规则和代码随报告存档。

吞吐至少3个独立进程、每进程30样本；正式p95门禁每进程至少300样本。区间跨阈值视为未定，不通过；继续采样，不删异常值直到通过。计时器精度、后台干扰和离群处理规则在正式采样前冻结。

Wasmtime与wasm-tools通常使用相关验证组件，独立于starshine但彼此不是完全独立验证实现；报告不得将二者夸大为两份独立形式证明。
